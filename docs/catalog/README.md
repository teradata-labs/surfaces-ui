# Surfaces analytics catalog

Layout, summary, data, discovery and conversation components for dashboards, query results and chat.

## Components

- [Text](components/Text.md): A heading, paragraph or caption.
- [Row](components/Row.md): Places children side by side. Wraps on narrow screens unless `wrap` is false. Children share the width equally unless `widths` gives each its share, or `sizes` says how each is sized (content width, fill, or fixed pixels); `sizes` wins over `widths` when both have one entry per child. `gap` and `padding` are steps of the theme's spacing scale.
- [Column](components/Column.md): Stacks children top to bottom. Use it as the root of most surfaces. `gap` and `padding` are steps of the theme's spacing scale.
- [Grid](components/Grid.md): Lays children out in columns that wrap onto new rows. Use it for dashboards: a row of numbers, then charts side by side. Columns are equal unless `widths` gives each its share, as when a person resizes them by hand. Children in a row are stretched to the tallest one; set `align: "start"` when the row mixes content of different heights, such as a chart beside a form, so each keeps its own height. `gap` is a step of the theme's spacing scale, between rows and columns alike.
- [Card](components/Card.md): A bordered container for one child, to group related content. `padding` is a step of the theme's spacing scale.
- [Divider](components/Divider.md): A thin line between sections.
- [Workspace](components/Workspace.md): Several children side by side as panels a person can arrange: drag a panel by its heading to another column or to an edge for a column of its own, resize with the dividers, and hide or show panels from a rail. `layout.columns` says where the panels are: a list of columns from left to right, each a list of panel ids from top to bottom, so search on the left and a map on the right is `[["search"], ["map"]]`. To rearrange, send the component again with a new `layout`; how a person left it comes back to you in the surface's controls as `layout`. Panels not placed are added to the last column. Each panel shows on a rail as an icon, with its name in a tooltip and, when a person turns names on, a short name under it: keep titles to a few words, and give `short` and `icon` so the rail reads well. Use it when a person will work across several views at once; use Grid or Row for a fixed arrangement.
- [SideNav](components/SideNav.md): Navigation down the side of a surface: groups of items, with the current one marked. A person can fold it away: it then keeps only a slim strip for its menu button, which slides it back in over the surface (never over anything outside it). In a narrow surface or on a narrow screen it is always folded. An item with `href` is a link (http and https only); one without sends the event with its `id`. Bind `current` to a data path to mark the item for what is showing.
- [Tabs](components/Tabs.md): Switches between several children, one visible at a time.
- [Button](components/Button.md): A control that sends an event back to the agent or opens a link. Its label is a child Text. To open a link, the action is a function call in place of an event: `"action": {"functionCall": {"@call": "openUrl", "args": {"url": "https://example.com/start"}}}`.
- [TextField](components/TextField.md): A labelled text box. The value is written to the data model at `value.path` as the person types, so other components (a Button's event context, a Text) can bind to it. Nothing is sent until a control sends an event.
- [NumberField](components/NumberField.md): A labelled number box. The value is written to the data model at `value.path` as the person types, so other components (a Button's event context, a Text) can bind to it. Nothing is sent until a control sends an event.
- [ChoicePicker](components/ChoicePicker.md): Pick one of a few options: radio buttons for four or fewer, a list for more. The value is written to the data model at `value.path` as the person types, so other components (a Button's event context, a Text) can bind to it. Nothing is sent until a control sends an event.
- [CheckBox](components/CheckBox.md): A yes-or-no box. The value is written to the data model at `value.path` as the person types, so other components (a Button's event context, a Text) can bind to it. Nothing is sent until a control sends an event.
- [DateTimeInput](components/DateTimeInput.md): A date, or a date and time (kept in UTC). The value is written to the data model at `value.path` as the person types, so other components (a Button's event context, a Text) can bind to it. Nothing is sent until a control sends an event.
- [Slider](components/Slider.md): A number chosen along a range, with its value shown in words. The value is written to the data model at `value.path` as the person types, so other components (a Button's event context, a Text) can bind to it. Nothing is sent until a control sends an event.
- [Form](components/Form.md): A form that checks what a person enters and submits it. Give the fields and their rules; the form draws a labelled input for each, shows errors beside them and sends nothing while any is wrong. A field with `visibleWhen: { field, equals }` is asked for only once another field holds that value. When the page has a forms backend, values go to the form with this `formId` there (the backend decides where they are stored; you never name a table); either way your event receives them. Use it instead of loose inputs and a Button whenever values must be checked or kept.
- [Stat](components/Stat.md): One headline number with a label, and optionally how it changed.
- [KeyValue](components/KeyValue.md): A short list of labelled facts.
- [Metric](components/Metric.md): One headline number worked out by the database from a query: a total, an average, a count. Use it for dashboard figures; use Stat only for a number you already have.
- [Badge](components/Badge.md): A small status label.
- [Progress](components/Progress.md): Progress toward a total.
- [DataGrid](components/DataGrid.md): A table over a SQL query, for any number of rows. Sorting and paging run in the database. Use it to show rows; use Chart to show a trend or comparison.
- [Chart](components/Chart.md): A chart over a SQL query. Give each measure an aggregate so the database summarises the data; without one the chart plots a random sample of rows. Each entry in y is a series; give series their own type and axis for a compound chart. Choose the form from the comparison: bars for amounts across categories (they are sorted largest first and start at zero), a line with xGrain for change over time, xBins for a distribution, scatter for two measures. Avoid a pie beyond five slices, more than five lines, and a second y scale (use two charts on the same x instead); the chart shows advice when its shape is hard to read.
- [PivotTable](components/PivotTable.md): A pivot table over a SQL query: row values down the side, column values across the top, summarised measures in the cells, with totals. The database does the grouping. Use it to compare a measure across two dimensions.
- [QueryResult](components/QueryResult.md): A query result a person can explore: filters; a table, a chart and a pivot of the same query; and the SQL that ran. Set `view`, `filters`, `sorts` and `columns` to put its controls in a given state; update them to change what a person sees, and they can go on changing them by hand.
- [Message](components/Message.md): One turn of a conversation, for a page that is laid out as a chat: who spoke, what they said (Markdown), and when. Put the turns in a Column, oldest first. `side: "end"` sets the person's own turns apart from everyone else's; the speaker is always written, so the side is never the only sign. Offer replies with Chips after the last turn, and take a typed one with a TextField and a Button. It shows a conversation; it does not run one.
- [Conversation](components/Conversation.md): A whole chat in one component: the turns so far, replies to pick, and a box to write in. Sending adds the person's turn to the thread at once and sends `send` with what they wrote. Give `messages` the turns, oldest first, or a data path holding them. Keep the thread there: answer `send` by adding the person's turn and yours to the list, and each is drawn once. For a prototype with no agent, `replies` answer in order, one for each turn the person sends. For one turn on its own, or a thread laid out by hand among other components, use Message.
- [RowList](components/RowList.md): One component drawn once for each row of a SQL query: a feed of posts, a list of cards, rows that each carry their own buttons. `child` is the component drawn per row, usually a Card. Inside it, and in everything it holds, a relative path reads the row's column of that name (`{ "@path": "author" }`; `formatString` with `${author}` too), and a Button's event carries the row's key the same way (`"context": { "post_id": { "@path": "post_id" } }`), so you learn which row was acted on. Absolute paths still read the surface's data model. The database sorts, filters and pages; a person asks for more rows, up to 200. An input inside a row must bind an absolute path. For plain rows in columns use DataGrid.
- [Markdown](components/Markdown.md): Formatted text: headings, lists, tables, links and code. Use it for explanations longer than a line.
- [Image](components/Image.md): A picture. `src` is a name the page knows (for example one it gave you), never a web address you choose: the page decides whether and where it loads, and when it does not know the name the `alt` text is shown in its place. Always describe what it shows in `alt`, which is required (an empty string only for decoration). Give `caption` for a line beneath it. `fit` and `maxHeight` keep it from taking over a layout.
- [CodeBlock](components/CodeBlock.md): Code with a copy button. For SQL a person should be able to run, use SqlProposal instead.
- [Table](components/Table.md): A small table of values you already have (at most 100 rows). For query results use DataGrid, which pages in the database.
- [Link](components/Link.md): A link to a web page. Only http and https addresses are shown as links; in a site, a path on the site ("/pricing") is too, and opens in place.
- [Checklist](components/Checklist.md): A list of steps showing which are done.
- [Chips](components/Chips.md): Short choices a person can pick with one press, such as follow-up questions or tables to look at. The chosen chip is sent back in the event context as `value`. An item is its text, or `{ label, value }` when what is sent differs from what is shown. Give `selected` a data path and a press also writes the chip's value there, inside the surface; bind another component's prop to the same path and it follows at once, with no agent: chips of table names whose values are SELECT statements switch a QueryResult whose `sql` is bound to that path. Set the path in the data model to the value that starts selected.
- [DecisionCard](components/DecisionCard.md): Asks a person to choose between options before you continue. Mark the option you recommend. The chosen option's id is sent back in the event context as `choice`.
- [Sparkline](components/Sparkline.md): A word-sized trend line beside its latest value, worked out by the database: no axes, grid or legend. Use it in a table of figures or beside a Metric to show direction; use Chart when the values themselves must be read.
- [BulletGraph](components/BulletGraph.md): One measure against a target and named bands (poor, fair, good), as a bar from zero. Use it instead of a gauge or a traffic light when a number needs judging against a goal.
- [StepFlow](components/StepFlow.md): Where multi-step work stands: onboarding, connecting a source, a cleaning or transformation run. Give a step the status `waiting` when the work has stopped for the person, and say in `detail` what you need from them.
- [PlanReview](components/PlanReview.md): A plan a person must approve before you act: cleaning steps, transformations, a connection to set up. List every step with what it changes; mark anything that removes or overwrites data or widens access as `risk: "high"` (it starts unticked). The event context carries `approved`, the ticked `stepIds` and any `note`. Do only the approved steps.
- [ActionReceipt](components/ActionReceipt.md): What happened after a person approved something: the outcome, who approved it and why, what ran, what changed, and whether it can be undone. Send one after every approved action that changed something, including a failed one. Give `undo` only when undoing is really possible, with `until` when it stops being; leave it out and the receipt says it cannot be undone. The `undo` event is a request: confirm it with the person before acting.
- [PiiReview](components/PiiReview.md): A review of a table's columns for personal data before it is shared, charted or sent to a model. Flag a column with the kind of data you suspect and how you know (`basis`); the person chooses the treatment and confirms. The event context carries `table`, `columns` (name, category, action) and `confirmed`. Never treat your own flags as the decision.
- [ThemeSwitch](components/ThemeSwitch.md): Changes how the whole page looks, at once: a built-in theme, light or dark, the accent colour, corner radius, font, density or chart colours. Leave out what should stay as it is. The person sees what changed and can undo it. To style only your own surface, put the same fields in `createSurface.theme` instead.
- [SqlProposal](components/SqlProposal.md): SQL you propose, shown for review. It never runs on its own: a person presses Run, and the result appears beneath it. The event, if given, is sent with `sql` when they do.
- [SqlEditor](components/SqlEditor.md): An editor for a person to write or change SQL. The event is sent with `sql` when they run it.
- [ObjectBrowser](components/ObjectBrowser.md): A tree of the source's catalogs, schemas, tables and columns, with the tables each one joins. Use it when a person needs to look around. The event is sent with `table` (and `column`) when they pick something. Give `opened` a data path and opening a table also writes its name there, inside the surface; bind another component's `table` to the same path and it follows, with no agent. The event is still sent.
- [ReportBuilder](components/ReportBuilder.md): A report built from pills: the dashboard pattern. `fields` are the report's pills (attributes, metrics, derived metrics), defined once so a metric means the same in every view. `tiles` are the views, each a set of shelves (`rows`, `split`, `values`, by pill id) drawn as a chart, a table, or headline numbers when there is nothing to break down by. Every tile follows `filters`, and a click on a bar filters the whole report. In build mode a person makes a view on the shelves and keeps it as a tile, edits pills, retitles, resizes and reorders; in view mode it is the dashboard alone with its filter bar. To write a report yourself, send `fields` and `tiles`; to leave it to the person, send only `sql` and pills are generated from its columns. What they change comes back as this component's controls, so read those first. Give `action` to show a box where they ask in words. Use it for anything with several views over one table or join; use separate Chart and Metric components only when the views read different queries.
- [SemanticModelEditor](components/SemanticModelEditor.md): A semantic model, to create, read and change: what one row is (the grain) and the columns that make it unique, where the rows come from (tables and joins, or a written query), and its dimensions (ways to break rows down), measures (a column summarised) and metrics (arithmetic over measures), each with who defined it. Every Explorer and ReportBuilder given this `model` takes its fields from it, so a change here changes every report on it. To propose a change, send `proposed` with the fields to add or replace (in the pill form: an attribute is a dimension, a metric a measure, a derived metric a metric), the names to remove and any change to the rows, and `proposedBy` with your name; read the model with describe_semantic_model first. To propose a new model, send `create` with its label and source and `proposed` with its rows and fields; read the tables with describe_table first and join from the table whose rows the model counts to tables that add one row of detail each. Either way it is shown as a draft, marked part by part and checked as it is made, and a person can change the joins, the grain, the key and every field before saving; nothing is kept until they save. What the person changes comes back as `proposed` in this component's controls. Give `action` to receive the `save` event, and the `ask` event with `text` when the person asks for something in words.
- [Explorer](components/Explorer.md): Exploring a query with pills, as a person would in a BI tool but with nothing defined in advance. Each field is a pill: an attribute to break down by, a metric (a column summarised) or a derived metric (arithmetic over metrics: a rate, a margin). Leave `fields` out and pills are generated from the query's columns; send `fields` to add your own metrics and calculations, which a person can then edit. `rows`, `split` and `values` are what is on the shelves, by pill id, and draw a chart and the numbers behind it, worked out by the database. A person drags, presses and edits; what they did comes back as this component's controls, so read those before changing it. Give `action` to show a box where they ask in words, sent as the event with `text`. Use it when someone wants to look around a table or a join themselves; use Chart when you already know the view.
- [FilterBar](components/FilterBar.md): Filters for a whole page: active filters as removable chips and a form to add one, with each column's values offered from the database and quick date ranges that stay relative. It writes the list to `filters`, a path in the surface's data model; give every Chart, Metric, Sparkline, DataGrid and PivotTable on the page `filters: { "@path": "/filters" }` with the same path and they all follow it. The views should read the same columns as `sql`, since a filter on a column a view does not have fails. Put the starting filters in the data model with updateDataModel. The event, if given, is sent with `filters` on every change.
- [FileBrowser](components/FileBrowser.md): A tree of folders and files: a source's storage (only the places it may read) and, with `local`, folders the person opens from their own computer, which their browser reads and nothing uploads. It shows names, sizes, dates and which table reads a file, never what a file holds. Use it when the data a person means is still files: to find what to bring in, or to see what a table reads. The event is sent with `path`, `name`, `place` and `format` when they open a file. You cannot read a local file; ask the person to load it.
- [ModelDiagram](components/ModelDiagram.md): A relationship diagram: tables as cards with their columns and lines between the columns that join. A person can drag columns together to add joins. Use it to show or agree how tables relate. The event is sent with `sql`, `tables` and `joins` when they press Use as query.
- [DataSearch](components/DataSearch.md): A search box over tables and columns, by name or meaning. The event is sent with `table` when a person opens a result. Give `opened` a data path and opening a table also writes its name there, inside the surface; bind another component's `table` to the same path and it follows, with no agent. The event is still sent.
- [ObjectDetail](components/ObjectDetail.md): Everything known about one table: description, certification, columns with statistics and related tables. Bind `table` to a path (`{ "@path": "/table" }`) to show whichever table a search or graph in the same surface opened. Give `opened` a data path and opening a table also writes its name there, inside the surface; bind another component's `table` to the same path and it follows, with no agent. The event is still sent.
- [RelationshipGraph](components/RelationshipGraph.md): A small map of one table and the tables it joins with or resembles. For several tables and their columns, use ModelDiagram. Give `opened` a data path and opening a table also writes its name there, inside the surface; bind another component's `table` to the same path and it follows, with no agent. The event is still sent.
- [NodeGraph](components/NodeGraph.md): Things and the links between them, drawn as a graph with the same things listed beside it: concepts in a glossary, tables in a model, systems and what they feed. You give the nodes and links; it reads no data. `group` is what kind of thing a node is (each group takes a colour and is named in the legend); `level` is how far along it is (drawn as how full the node is). Give `selected` a data path to mark the open node and to write the node a person opens there. Past 300 nodes it shows what is around the open node and says how many it left out. For tables and their joins use ModelDiagram; for a pipeline use PipelineGraph.
- [AskData](components/AskData.md): A question box that answers from the catalog and cites the tables it used.
- [ContextBuilder](components/ContextBuilder.md): Lets a person assemble the tables, columns and notes an agent should work from, and preview exactly what the agent will receive.
- [QueryPlan](components/QueryPlan.md): How the database intends to run a query, without running it: the steps as a tree and the engine's own plan text. Use it to explain why a query is slow.
- [SourceList](components/SourceList.md): The data sources available, how each connects (by secret name only) and a button to test that its tables can be reached.
- [PipelineGraph](components/PipelineGraph.md): A pipeline as a graph of sources, tables, views and sinks with the flows between them and each one's latest status. You supply the nodes and edges as the pipeline engine reported them. The event is sent with `id` and `name` when a node is chosen.
- [PipelineView](components/PipelineView.md): A pipeline the backend runs, live: its datasets and how they feed one another, its runs, and for each dataset its query, grain, key, columns, row rules and checks with the latest results, with buttons to run, check or rebuild it. Give `action` to hear when a person's run starts and ends (`started`, `finished`). Use PipelineGraph instead when you only have a description of a pipeline to draw.
- [DatasetReview](components/DatasetReview.md): A new or changed pipeline dataset for a person to approve: its query, what it reads, its grain and key, columns and checks, and what changes from the saved version. Give it exactly what `propose_dataset` returned: `pipeline`, `dataset`, `expectedVersion` and `digest`. The person may change the grain, descriptions and checks, names themselves, and approves or rejects. Approving saves it on the server, which checks it again; it builds nothing, so run the pipeline afterwards if they want it built. The `decide` event says what they chose.
- [IngestWizard](components/IngestWizard.md): Steps a person through bringing new files in: where they are, what the engine finds there, and which columns to keep, rename and retype. It writes configuration to review; it loads nothing.
- [RunHistory](components/RunHistory.md): The runs of a pipeline, newest first: how each ended, how long it took, what it refreshed and why it failed.
- [ExpectationsPanel](components/ExpectationsPanel.md): Data quality rules for a pipeline with how many records passed and failed each, worst first. Counts come from the engine.
- [SchemaDiff](components/SchemaDiff.md): How incoming data differs from the table it loads into: new, missing and retyped columns.
- [StreamMetrics](components/StreamMetrics.md): How a streaming query is keeping up: input and processing rates, batch size and duration, with recent trends. Give the progress reports oldest first, as reported.
