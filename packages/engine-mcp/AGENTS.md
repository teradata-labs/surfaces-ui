# `packages/engine-mcp`

Agent notes for this folder. The rules that hold everywhere are in the root [AGENTS.md](../../AGENTS.md). What you learn about this folder goes here.

| Path | What it is |
|---|---|
| `packages/engine-mcp` | A database's own MCP server behind the `Engine` interface. `createMcpEngine({ dialect, transport, tool?, argument?, arguments? })` connects as an MCP client (`mcpSql`), finds the server's query tool, and sends the SQL the rewriter wrote for the dialect through it. `stdioServer(command, args, { env })` (`@surfaces-ui/engine-mcp/node`) starts a local server and passes on only the environment variables named; `httpServer(url, { token })` calls a remote one. Read-only: no kept results, pipelines, time travel or cancelling a sent query. Config on the dev server: `{ id, engine: "mcp", dialect: "postgres" \| "duckdb" \| "teradata", server: { command, args?, env? } \| { url, secret? }, tool?, argument?, arguments? }`; the token of a remote server is read from `<SECRET>_TOKEN`. |

## Why it exists

A host such as Claude holds a connection to each MCP server, and one server cannot call another through it. So data that a database's MCP server holds cannot reach the components in the Surfaces MCP app unless the Surfaces server connects to that server itself. This package is that connection. It keeps rule 2: the database does the sorting, filtering and paging, and rows go from the data server to the page, never through the model.

## Rules

- **No server takes bound values, so values are written into the statement, and must never be able to change it** (`literal.ts`). Numbers are checked to be numbers. Postgres text is dollar-quoted with a tag the value does not contain: a dollar-quoted string has no escapes whatever `standard_conforming_strings` is, and it is an untyped literal, so a date sent as text still compares with a timestamp column (a hex-decoded value is typed text, and Postgres refuses to compare it with a date). DuckDB and Teradata text is single-quoted with quotes doubled, since neither reads a backslash as an escape. A dialect whose strings do read backslashes (MySQL) needs its own form before it is added; do not reuse quote doubling for it.
- **A result must arrive with its types, or the components draw wrong.** Most servers return JSON with no types, and the common drivers send a decimal or a 64-bit count as text (seen live: the reference Postgres server returns `SUM(amount)` as `"2500050.00"` and `COUNT(*)` as `"5000"`). Guessing "text that looks like a number is a number" would turn a postcode into one. So per dialect:
  - **Postgres**: every query is sent as `SELECT row_to_json(t) FROM (<query>) AS t`, so a number is a JSON number and text is text whatever driver the server uses, and the types come from one probe per query shape, `pg_typeof` over the query joined to a single row on a condition that is never true: Postgres never runs the query, yet its columns are there to name and to ask the type of. The same probe gives the columns of a result with no rows, which a filter bar needs. The probe is kept per statement without its `LIMIT` and `OFFSET`. `numeric` arrives as a float: `pg_typeof` does not give its precision, and `row_to_json` values pass through JSON numbers, so a number past 15 digits loses its last ones.
  - **DuckDB** (the MotherDuck server): the answer carries `columns` and `columnTypes`, with or without rows, so it is one query and decimals are exact.
  - **Teradata**: the server names each column's Python type (`int`, `Decimal`, `date`, `datetime`, `str`), mapped to Teradata type names for the Teradata engine. The server has already turned a `Decimal` into a float.
- **Teradata goes through the Teradata engine**, not a second copy of it: `teradataMcpClient` is a `TeradataClient` (as Query Service and the driver are), so the dictionary queries, the read-only guard and the Arrow types are that engine's. The server owns the session, so the time zone and default database are its connection's, not UTC as the other transports set. `row_limit: 50000` is sent with every query (the server stops at 1,000 otherwise) and `persist` is never sent, since it makes the server create a table.
- **Rows are turned into Arrow by the Teradata engine's `arrowResult`**, with each database's type names mapped by `standardType`. It lives there for history's sake; moving it to `@surfaces-ui/engine` would let this package drop that dependency for the other dialects.
- **A result the server cut short is an error, never a short result** (`truncated`), as on Teradata: a chart over half the rows is wrong without saying so. A page of a grid is well under any server's limit; a CSV export of a large table is not, and fails with the reason.
- **The query tool is found by its shape** (`findQueryTool`): a tool with a text argument named `sql`, `query` or `statement`, a read-only form preferred where a server has both. The argument is not required to be marked required, because the Teradata, reference Postgres and several other servers leave that out. `tool` and `argument` in config override it; `arguments` adds fixed ones (a project id).
- **`readRows` reads the answer shapes servers really use**: a list of row objects, an envelope around one (`results` with `metadata.columns`; `columns`, `columnTypes` and `rows`), one JSON object per text block, JSON inside prose between `<untrusted-data-…>` tags, structured content, and a Python literal (`python.ts`, which reads and never evaluates). Add a shape there with a test that holds the server's real answer.
- **How a server is reached is never shown or repeated.** A command line or an address can hold a connection string, so a source shows only the program or the address without its query, a failure to connect says only that the server could not be reached, and a database's error is cut to its first line, since a driver's message can run on into a stack trace.
- The catalog (schemas, tables, columns, keys, comments, row counts) is read with SQL through the same query tool, not through each server's own listing tools, so it is the same for every server of one database. Postgres keys and comments come from `pg_catalog`: `information_schema` shows a table's constraints only to a role that owns it or may write to it, which a read-only login is not.

## What has run

- **Live, the whole stack** (`packages/dev-server/src/mcp-source.test.ts`, which runs when `SURFACES_TEST_MCP_POSTGRES` or `SURFACES_TEST_MCP_DUCKDB` is set): Postgres 16.15 through `@modelcontextprotocol/server-postgres`, and DuckDB 1.5.6 through `mcp-server-motherduck`, each over stdio. Listing, describing with keys, sort, filter and page, totals by group, month buckets, a date sent as text, median and percentile, a sample, values that try to end the statement, a result with no rows, a join, and unknown columns and tables. Every expected number is worked out in the test from the rule the seed generates rows by.
- **The Teradata MCP server** (4.2.6) was started and its tool list read: `base_readQuery` is found, with `sql`, `persist` and `row_limit`. No Teradata system was within reach, so its answers are tested against a stand-in built from its source (`engine.test.ts`); the envelope, the column types and `truncated` have not been seen from a real system.
- **Read from each server's source, not run**: Supabase (`execute_sql`, rows inside prose), Google's MCP Toolbox (one row per block), `crystaldba/postgres-mcp` (a Python literal; its current release does not start), Snowflake, BigQuery and Databricks servers (their tool names are in `KNOWN`).
- **Not built**: MySQL, SQL Server, Snowflake, BigQuery, Databricks and Oracle, which each need a dialect in `@surfaces-ui/sql` first (MySQL and MariaDB also need a typed-result form, since their servers send decimals as text and dates in the server's zone); servers that answer later and must be polled (Databricks, BigQuery); a server with no SQL tool (Microsoft's SQL MCP Server reads entities); OAuth to a remote server (only a bearer token); `store`, so each view of a query runs it again.
