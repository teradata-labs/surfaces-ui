# Surfaces UI — guide for agents

Guides for people and agents using the library in their own projects: [docs/getting-started.md](docs/getting-started.md), [docs/agent-integration.md](docs/agent-integration.md), [llms.txt](llms.txt). Keep them current when an exported API changes. [docs/packages.md](docs/packages.md) and each package's README are written from its `package.json` by `scripts/package-readmes.mjs` (`--check` in `pnpm check:release`); a new package goes into one of its `GROUPS`.

Surfaces UI is a UI library for data and analytics users: exploring schemas, querying, charting, tables at scale, chat, and composing pages and apps. The approved plan with the full architecture and phases is in [docs/plan.md](docs/plan.md). Read it before adding a package.

## Status

Phases 1 (foundation), 2 (data core, DuckDB only), 3 (core components), discovery with agent context, most of phase 4 (catalog, A2UI rendering, MCP Apps) and the chat half of phase 5 (agent interface, chat thread components, every component drawable in a thread, and `AnalyticsChat` with attachments, agent choices, voice and saved conversations) are in place. The Loom adapter has run against a live Loom server with a local model (text replies, a session carried across turns, usage, and a chart drawn from an `a2ui` block); tool steps, questions that pause a turn, and a signed-in server are covered only by tests on recorded events. DataFusion runs through `@surfaces-ui/engine-datafusion` against DataFusion 47 served by ROAPI over HTTP (`packages/dev-server/src/datafusion.test.ts`, which runs only when `SURFACES_TEST_DATAFUSION` is set); Arrow Flight SQL, the Rust sidecar and Delta or Iceberg tables on DataFusion are not done. `AgentService` runs over Connect (`agentRoutes`, `connectAgent`). The Claude adapter has run live once through the dev server (a composer turn on Opus 5.5); beyond that it is tested against recorded streams. Reading tables and listing files over an S3-compatible store has run against a local stand-in (`scripts/s3-sim.sh`, the adobe/s3mock container; `packages/dev-server/src/s3.test.ts`, which runs only when `SURFACES_TEST_S3` is set), with and without credentials; real S3, GCS and Azure storage and a real Iceberg REST catalog have not been run. Derived measures have run on DuckDB, on the stand-in and on a real Teradata system. Pipelines run only on DuckDB through the reference runner, headless through `surfaces-pipelines` as well as from the UI, with checks over built datasets and saves a person approved; the pipeline agent tools are tested against the memory backend and over MCP in process, not yet with a live model; a dbt project is read from its artifacts and built by dbt itself (`@surfaces-ui/pipelines-dbt`), run against a dbt-duckdb 1.12 project and not yet against another warehouse or dbt Cloud; nothing has run on Spark, and the streaming display components (`StreamMetrics`, `SchemaDiff`) have no backend. Standalone app builds and embeds are not built; site-catalog pages can be served from a Next.js app (`@surfaces-ui/next`), built with static export by a real `next build`, with no layouts yet. The wire format is A2UI v1.0 (v0.9 is still read): the move is covered by unit tests on every package that touches A2UI, and no live model has drawn with the v1.0 prompt yet. Developer tools (slice 1 of 3) are built in the browser: `@surfaces-ui/trace` and `@surfaces-ui/devtools` record and show messages, components, problems, state, events, agent turns and service calls, with time travel; run in the playground with the scripted agent and DuckDB in the page, and in the browser tests. Not built: a `traceparent` header on Connect calls, a `TraceService` and server spans, a standalone page on the dev server, export and import of a trace, root cause analysis beyond the fixed rules of `componentFindings` (nothing reads a trace with a model, and causes are found for one component at a time), a json-render source map (a json-render spec is recorded only when a host records it), the MCP app host, and a browser extension. Dragging panels inside the popped-out window is not verified (keyboard and menu moves work); the Chrome Performance tracks are written to the documented API and tested against a stub, not looked at in Chrome's panel. Only what is listed under "What exists" is built; everything else in the plan is not yet. The Teradata engine adapter (`@surfaces-ui/engine-teradata`) has run against a real Teradata system (20.00) through the `teradatasql` Node driver (the live suite, 12 of 12, and the playground workbench); the Query Service transport has still not run against a real Query Service.

## What exists

**UI layer** (must work with the data layer removed)

| Path | What it is |
|---|---|
| `proto/surfaces/v1/*.proto` | The contracts: `QueryService`, `CatalogService`, `SourceService`, `ViewService`, `DiscoveryService`, `ContextService`, `AgentService`, `PipelineService`, `IngestService`, `ModelService`, `SemanticService`. Source of truth for anything crossing a process boundary. |
| `packages/proto` | TypeScript generated from the protos (`src/gen`, never edited by hand). |
| `packages/tokens` | Theme contract (`Theme`, `parseTheme`), presets, colour derivation, `themeCss`, `echartsTheme`. No dependencies, no DOM. |
| `packages/data` | The `DataSource`, `Discovery` and `Pipelines` interfaces every component uses, Arrow IPC framing (`encodeBatch`, `decodeStream`), `collect`, and `memoryDataSource` for tests and demos. `ModelSettings` (`modelSettings` over backend handles, `memoryModelSettings`): which model each agent backend runs, and the choice of another, with no key in it. `Semantics` (`semantic.ts`): semantic models, a query with dimensions, measures and metrics, each saying who defined it, versioned (`memorySemantics`, `semanticModelProblems`, `semanticModelDataProblems`, `semanticModelJson` / `semanticModelFromJson`, `StaleSemanticModelError`, `SemanticModelError`). A model on a pipeline dataset (`semantic-pipeline.ts`): `semanticModelFromDataset`, `datasetStanding`, `semanticDatasetProblems`, `datasetSql`. |
| `packages/components` | React components (see the table below) and `styles.css`. `app-components` (`appComponents.ts`): the components an app places itself, described once as data (`AppComponentDoc`: plain props as JSON Schema, `parts` that take code, `callbacks`, `example`), each checked against its props type by `describeAppComponent<Props>()`; `appComponentMarkdown` and `appComponentCode` write their docs page and JSX. `@surfaces-ui/chat/app-components` holds the chat's three and `@surfaces-ui/devtools/app-components` the dev tools. |
| `packages/agent` | The `AgentBackend` interface (one `send` is one turn, streaming text, steps, surfaces, approvals, usage), event helpers, `scriptedAgent` for tests, `extractSurfaces` for models that can only write text (a message ends where its brackets close, so one written over many lines or a list of them is read; text in a block that is not a message is never dropped quietly: the block ends in one `error` event, `UNREAD_SURFACE`), `turnText` (a turn's event, surface state, contracts and problems as text for a model) and `toolCallingAgent` (any model with tool calls; the host writes `complete`, the model draws through `render_surface`; `checkSurface` returns catalog problems to the model in the same turn; a tool with `approval` pauses the turn for a person and runs only what `checkApproval` accepts). `offer` on `toolCallingAgent` (`AgentOffer`, `choices.ts`) says what a person may choose: models, skills (text added to the system prompt while on) and connectors (sets of tool names, on or off; tools no connector names are always on); every turn is checked against it (`resolveChoices`) and anything not offered, or a connector not connected, is refused, never trusted from the client. `describeAgents()` reports it (`DescribeAgents`), and `agentRouter` puts several agents behind one backend, a turn going to the one its `agentId` names. `dataTools(dataSource, { sourceIds })` gives an agent `list_tables` (with `search` and `database`, and the source's SQL dialect in the answer) and `describe_table` (names, types, keys, descriptions and declared joins; never values); a table in a database is named `database.table` both ways. `approvals.ts`: `approvalDigest`, `withDigest`, `checkApproval`. |
| `packages/agent-anthropic` | `anthropicAgent({ client, system })`: `toolCallingAgent` over Claude's Messages API with the official SDK (a peer dependency). Defaults: `claude-sonnet-5-5`, effort "high", streaming, cached system prompt, eager tool input streaming, server-side refusal fallbacks on (`fallbacks: false` off). Claude's content blocks are sent back unchanged; a refusal or a tool call cut off by `max_tokens` stops the turn. Tested against recorded streams, and run live once through the dev server (Opus 5.5 built a chart and a sparkline over the retail seed in the composer, passing the catalog); tool steps and approvals have not been run live. |
| `packages/agent-openai` | `openAiCompatibleAgent({ baseUrl, model, headers })`: `toolCallingAgent` over `/chat/completions` (OpenAI, Ollama, vLLM, LM Studio), `fetch` only. Run live against a local model through Ollama. |
| `packages/create-surfaces` | `npx create-surfaces <dir>`: writes a Vite app (a dashboard `PageDocument`, a chat over `connectAgent`) and a `surfaces.config.ts` (seeds, `anthropicAgent` when `ANTHROPIC_API_KEY` is set). It installs the released packages from npm; `--from-repo <checkout>` packs a checkout's packages into `vendor/` instead, to try changes that are not released yet. |
| `packages/chat` | Chat threads. `Chat` (everything), or `useChat` with `MessageList`, `Composer`, `ToolSteps`, `ApprovalCard`, `Suggestions`, `UsageGauge`. Replies hold Markdown, tool steps, approvals and any catalog component drawn inline. `reduceThread` is the pure reducer. A host that keeps its own thread can add an `actions` part (`ChatActions`, drawn by `ActionsCard`): buttons under a reply, or alternatives one row each (`choices`) with buttons for the whole set after them; presses reach `MessageList`'s `onPartAction(partId, actionId, choiceId?)`, a disabled button stays focusable with its `reason` read, and `outcome` replaces the buttons once handled. `ChatComposer` takes `context` (`ComposerContext`: chips for what a message is about that is not data, removable through `onClear`) and `toggles` (`ComposerToggle`: checkboxes for the next message, kept by the host). `user` says who decides; `storage` keeps the thread across reloads (checked by `parseThread` on load). `ApprovalCard` checks the digest, edits, reasons, typed confirmation, expiry and multi-person approvals. `Chat` and `PageStudio` draw with `lazyAnalyticsRenderers`. **A conversation is a document.** `conversationDocument(thread, { id, title })` turns a thread into plain JSON, `parseConversation` checks one from anywhere before use, and `Chat` opens on one with `initialThread` (`conversationThread`) and reports every change through `onThreadChange`; a library keeps it as a saved surface of kind `conversation`. **`AnalyticsChat`** is the chat for data people: a `Workspace` with its rail on the right, the conversation always shown, and panels only for the props given: `sessions` (Conversations: `SessionList` over `ChatSessions`, `librarySessions(library)` or `memorySessions()`), `browse` (Data: `DataPanel`, tables and files), and `agents` or `providers` (Agent setup: `AgentSetupPanel`, in full: every model under its provider with where it runs (`ModelsPanel`), the agent, its skills and its connectors). Its composer is `ChatComposer` (`Composer` is the same): `attachFiles` (the `+` menu, drop and paste; any file, the host says what became data), a Model menu of its own (`ModelMenu`, switched often and showing who answers; given `providers` (`ChatProvider`: where models run, each with its models) it groups every model under its provider, a few from each and "View all N models…" opening the setup panel, a pick sets `provider` and `model`, and the host turns that into its own backend, so neither is sent with the turn) and one Agent setup menu (`SetupMenu`) whose sections, Agent, Skills and Connectors (Tools and Data), open in place with a Back row (Enter or → in, ← or Escape back; with one section it opens on it); a few items each, then "View all…" or "Manage…" opening the panel, `speech` (`SpeechAdapter`; `browserSpeech()`; `useVoice` dictates or holds a spoken conversation) and a round arrow-up Send. The person's choices are `ChatSettings` (`agentId`, `model`, `provider`, `skillIds`, `connectorIds`, `sourceId`), sent with each turn by `useChat`'s `settings`. `Chat` and `PageStudio` use the same composer and take `settings`, `onSettingsChange`, `providers` and `onManageProviders` too. A conversation written out as data (`ConversationScript` in `@surfaces-ui/spec`) becomes a played thread with `scriptThread(script, catalog, turns?)` or an agent that answers from it with `scriptAgent(script, { catalog, played })`: a message matching a turn gets that turn's reply, an event from a drawn control gets the script's `events` answer, and anything else is told what it can answer. Its replies are shown as answered by the script's `answeredBy`, which must say it is not a model. |
| `packages/state` | State services with no React or DOM dependency: `createStore`, `derive`, `withHistory` (undo), `persist` (any `StateStorage`, versioned, checked on load; `select` saves a part and `restore` puts it back; a change made while loading wins), `syncUrl`, `createViewState` (a shared plain filter list (`FilterSpec`) and sorts for cross-filtering; `viewFilters`), `createQueryRuns`. `@surfaces-ui/state/react` has `useStore` and `useHistory`. |
| `packages/trace` | Tracing, with no React, DOM or data-layer dependency. A `TraceEvent` (`id`, `seq`, `time`, `traceId`, `spanId`, `parentId` in W3C trace context form (`traceparent`, `parseTraceparent`), `kind`: message, component, problem, state, event, agent or service, `name`, `status`, `durationMs`, `surfaceId`, `componentId`, and a plain-JSON `detail`); `createRecorder({ limit })`, a bounded log shaped like a store (`get`, `subscribe`, told once per task; `record`, `start` for a span, `update`, `clear`); wrappers for backends passed outside the providers: `traceService(name, service, recorder)` (any object; a method that returns a value, a promise or an async iterable), `traceDataSource` (a query's SQL, executed SQL, notices, columns, row and batch counts, time, and an error's code and position) and `traceAgent` / `agentTurn` (one turn is one trace: the request, text, steps, approvals, usage, the error); `recordMessage`; `replay(events, seq, { apply, setPath })`, `traceSteps`, `diffJson` and `stepDiff`, pure, for time travel (the surface model's `applyMessage` and `setPath` are handed in, since this package sits below `@surfaces-ui/spec`); `recorder.inspect({ surfaceKey, componentId })` points at one drawn component (`inspected`, `onInspect`; nothing is recorded) and `recorder.pick(on)` turns picking on, and the `SurfaceView` that drew a component then puts one hidden, empty `template` before it (`INSPECT_MARK` holding the surface's key, `INSPECT_COMPONENT` its id, `INSPECT_POINTED` on the one pointed at), there only while that component is pointed at or picking is on, so a tool finds a component's element, and the component an element belongs to, without components being wrapped; `performanceTracks(feed)` shows finished spans as custom tracks in Chrome's Performance panel (`performance.measure` with `detail.devtools`; tested against a stubbed `performance.measure`, not yet looked at in the panel). `@surfaces-ui/trace/react` has `TraceProvider`, `useRecorder`, `TraceScopeProvider`, `useTraced` and `useProvided`. **A trace never holds row values, Arrow batches, file contents or credentials**: everything recorded goes through `plain` (binary becomes its length, a value under a credential-like key is withheld), and of an answer only `responseSummary` is kept (numbers, flags, list sizes, and text only where the field is a name, a code or SQL; lists are never walked). |
| `packages/devtools` | `SurfacesDevTools`: one component placed around an app. It makes the recorder and the `TraceProvider`, renders its children, and shows a floating button (and Ctrl+Shift+D, ⌘⇧D on a Mac) that opens a panel docked to the bottom or the side, resizable (drag, or arrows on the divider), which can move to a window of its own (the same panel drawn into the other window's document, so no route or channel is needed). `enabled` defaults to on in a development build (`process.env.NODE_ENV`) and absent in production; nothing a visitor can set turns it on. Off, it renders its children alone and loads no panel code (`./panel` is a lazy import, a chunk of its own). The panel (`DevToolsPanel`, `@surfaces-ui/devtools/panel`) takes a plain `TraceFeed` and never calls a model: a `Workspace` of Timeline (every event, by kind and status, newest or oldest first), Messages (as it arrived, as it was read, what the catalog said), Components (the tree from `surfaceOutline`, props as sent and after bindings, problems per component; picking one outlines it on the page and scrolls it clear of the drawer, through the panel's `onInspect`, which the shell hands to `recorder.inspect`, and narrows Timeline, Events and Services to what that component did, Messages to the messages that sent it and State's controls to its own, with an "Only …" chip in each that clears it; the bar's "Pick a component on the page" does the same from the page: the component under the pointer is outlined and a press picks it without reaching the page, Escape gives up, and the Components list is the keyboard way; a picked component also gets "Likely cause", there and over the narrowed Timeline: `componentFindings` (`cause.ts`), a pure function over the events and the surface that calls no model and runs no query, listing most likely first a refused message, what the catalog said, a component nothing draws, a container that failed, a binding to an empty place in the data model, a query that failed (code, line and column), a component that threw, an event its contract refused, a query with no rows, a cancelled call and a slow one, each with a Show button that opens the recorded event, a call no longer counting once the same method answered after it ended; it says it is rules and not a model, and an empty list says only that nothing recorded points at a problem), State (data model, a person's writes, controls, what the step changed), Events (actions with the contract result, context notes), Services, Agent (a turn is one row, and opened it is laid out as it went: what was asked, each step and tool call, approvals asked for, the reply, how many surface messages it sent, who answered and usage), and Surface: the surface as it stood at the step the scrubber is on, drawn read-only with `SurfaceView` over the backends the page's providers handed the recorder, with a notice that its data is queried live. Lists are windowed. Its styles are added as a `<style>` element (`styles.ts`), tokens only. `surfacesAt`, `surfaceStepDiff`, `componentFindings`. Described in `appComponents.ts` (`@surfaces-ui/devtools/app-components`). |
| `packages/spec` | Agent-generated UI. `defineCatalog`, `basicsCatalog` (the components every catalog shares), the `analyticsCatalog` built on the same definitions, and the `siteCatalog` (`extendCatalog(basicsCatalog, …)`: Hero, Section, FeatureGrid, DeviceFrame, PromptReveal, Showcase, NavBar, Footer, Media, Quote, Callout, PostCard, PostList; `siteRenderers`, `siteMarkup`, docs in `docs/catalog/site`); the A2UI v1.0 surface model (`applyMessage`), which still reads v0.9 (`upgradeMessage`, `upgradePage`, `upgradeSurface`); generators (`catalogJson`, `catalogPrompt`, `catalogDocs`, and `surfaceAgentPrompt(catalog, { dialect, draw, dataTools })`, the system prompt for an agent that builds and changes surfaces over real data); `fromJsonRender`. `@surfaces-ui/spec/react` has `SurfaceView`, `useSurfaces` and `analyticsRenderers`. **Arranging by hand** (`arrange.ts`, `react/arrange.tsx`): `useArrange({ surface, catalog?, apply, say, remove, resizeWhileViewing?, selected?, onSelect? })` gives any host a person's Arrange (frames to drag by a bar or move by keyboard, before, after, beside or into another, with a line in the gap where the component will land (`.sf-arrange-insert`) and the receiving container outlined (`data-receiving`); handles for heights and a `Grid` or `Row`'s widths; and, on the selected container (a click on its frame or focus on its bar; `selected` and `select`), handles in its gap and at its padding (`.sf-arrange-space`) that step token to token, labelled "16 px · space-4", sent as `spaceMessages`), with `ArrangeToggle`, `ArrangeHelp` and `ArrangeGhost`; each change comes back as the A2UI an agent would send (`moveComponentMessages`, `stepComponentMessages`, `besideMessages`, `besidePageMessages`, `heightMessages`, `gridWidthsMessages`, `removeComponentMessages`, `surfaceOutline`, `placeOfComponent`). Its handles are `ResizeHandle` (`@surfaces-ui/components`), the one resize handle there is; Enter or a double click on one makes the widths equal or takes the height off. With `resizeWhileViewing: true` the width handles between a `Grid`'s or `Row`'s columns, and the height handle under a component whose `height` or `minHeight` is set, stay while nobody is arranging (on a plain `.sf-arrange-view` box): a drag sends the same messages as one step, `layoutEdits` keeps it and a locked component can still be sized; moving and removing stay inside Arrange, and Arrange's frames replace these handles while it is on, so one layer shows. A host passes `arrange.surfaceFrame` (Arrange's frames, the viewing handles, or nothing) as `SurfaceView`'s `frame` and draws `arrange.shown(surface)`. `PageStudio` takes `resizeWhileViewing` beside `arrange`; the pages gallery and the Playground area turn it on. It is optional: nothing draws differently without it. Grid and Row renderers mark themselves `data-arrange-container`; the styles are `sf-arrange-*` in `@surfaces-ui/components/styles.css`. `ConversationScript` (`conversation.ts`) is a conversation as plain data: turns of what a person says and the text, steps and surfaces the agent answers with, plus `events` (answers to a drawn control's event, with `{{key}}` filled from the event's context). `validateConversationScript` checks every surface against the catalog; `scriptSurfaces` lists them. |

Component rules:
- A chart over a large table must use an aggregated measure (`y={[{ column, aggregate: "sum" }]}`), which sends `group_by` and `aggregates` in the `ViewQuery` so the engine summarises. Without an aggregate the chart asks for a random sample (`ViewQuery.sample`), never "the first N rows".
- A time series sets `xGrain` and a histogram sets `xBins` or `xBinWidth`; both become `ViewQuery.buckets`. Never group by a raw timestamp.
- A row with no x cannot be placed on a time or number axis: it is left out of the option whole (`rowsWithoutX`), so a bucket that is not drawn never sizes the y axis, and the chart says beneath itself that rows with no x are not drawn (with what the one such row holds). A category axis draws it under "null".
- Axis titles are placed from the tick labels, not from the axis line (`nameMoveOverlap`), and the plot shrinks until labels and titles fit (`grid.outerBoundsMode: "same"`, `outerBoundsContain: "all"`). Do not go back to `containLabel` with a fixed `nameGap`: it fits one width of tick label only.
- Each `y` entry is a series. A compound chart gives a series its own `type` and puts a measure on another scale with `axis: "right"`.
- Chart defaults follow the chart-standards skill; do not undo them. Bars over categories are sorted largest first (`sort="x"` keeps the column's order); the sort is sent to the engine so a row limit keeps the largest, and a split chart is ordered by each category's total. Dates, bins and numbers keep their own order. Up to four lines whose ends are apart are named at their ends instead of in a legend. The zoom bar appears only past 60 points. A chart whose drawn shape misleads (`drawnShape` then `chartAdvice`) says so beneath itself; pass `advice={false}` only for a chart that is not there to be read, such as a colour test card.
- Examples and demo agents must pass their own advice: no pie where bars would do, no second y scale, and a comparison (a `Sparkline` or a `BulletGraph`) beside headline numbers.
- Totals in `PivotTable` are separate grouped queries, because averages, medians and distinct counts cannot be added up from cells. Do not sum cells in the browser.
- **What a data component says to people is the page's to write.** `Chart`, `DataGrid`, `PivotTable`, `QueryResult`, `Metric`, `Sparkline`, `BulletGraph` and `RowList` take `emptyMessage` (in place of their own text when the query answers with no rows) and `errorMessage` (in place of the engine's error text when it fails), both `DataMessages` and both catalog props (`MESSAGES` in `analytics.ts`). The alert stays `role="alert"` and keeps the engine's text in `data-error` (and `DataGrid` in `onInfo`) for developers; people read only the message.
- Every view of one run passes the same `notBefore` (an ISO time, set when Run is pressed). A backend that keeps results runs the query once for all of them; a later `notBefore` runs it again.
- A grid does not count rows when the answer is already known (a kept result, or a first block that is not full). Do not add a count call that runs on every load.
- Export with `exportCsv(dataSource, request)`: it streams the whole result from the backend, a batch at a time, so the file is not limited to the grid's window (the backend's row limit still applies and is reported). Never build an export from the rows a grid happens to hold. CSV text that a spreadsheet would run as a formula is defused in `csvField`; keep that.
- Column formats (`formats={{ amount: { kind: "currency" } }}`) change how a value is written, never the value: sorting, filtering and export use the real data.
- The values offered in a filter come from the engine (`loadValues`, a grouped count), not from the rows on screen.
- A plan is fetched only when a person asks for it; explaining is a call to the engine.
- Errors: a `DataSource` may throw `QueryError` (from `@surfaces-ui/data`) with `code`, `line` and `column`; read any error with `queryErrorInfo` and pass the position to `SqlEditor`.
- `Chart` reports clicks through `onPointClick`. For cross-filtering, keep the selection in `createViewState` and give each view `view.filters(ownColumn)`, so a chart never filters away the bars a person clicks. The view state holds the same plain filter list (`FilterSpec`, from `@surfaces-ui/data`) as page-wide filters and agents, and a click follows one rule everywhere (`toggleValueFilter`): a second value is added (`in`), a chosen one is taken out.
- `PipelineGraph`, `RunHistory`, `ExpectationsPanel`, `SchemaDiff` and `StreamMetrics` are display only: they draw what an engine reported and take plain data props. `PipelineView` and `IngestWizard` talk to a `Pipelines` backend. Neither kind computes the graph, rates or quality counts in the browser.
- `ModelDiagram` refuses joins that cannot work (`checkJoin`: a table to itself, a missing column, nested or binary keys, keys of different kinds such as a number against text) and says why in an alert. The form offers only columns that could match. A join that turns out not to work (a suggestion, or a column that has gone) stays visible, is marked, and is left out of the generated SQL, as is a table that could not be read (with "Try again"). Every line has its own remove button; a join that closes a loop is allowed with a warning.
- `PlanReview`, `PiiReview` and `StepFlow` only report a decision or show a status. Nothing in them runs SQL, registers a table or changes data; whatever acts on a decision is the host or the agent, through the usual read-only and pipeline paths.
- `piiHints` reads column names only. Scanning values for personal data is allowed only on a source in `allowSampleValues`. Engine-side masking functions are not built: a treatment is written as SQL in a pipeline dataset and reviewed by a person.
- `ModelDiagram` must stay usable without a pointer: every join can be added, confirmed and removed from the list and form beneath the canvas. Joins it suggests stay "Inferred" until a person confirms or draws them.
- `ModelDiagram` and `PipelineGraph` pan and zoom through `usePanZoom` (with `PanZoomControls`): drag the background or scroll to pan, Ctrl/⌘ + wheel or pinch to zoom about the pointer, buttons for zoom in, zoom out, fit and 100%, and `+` `-` `0` and arrows on the focused canvas. The view fits the content on first draw and until a person takes over; zoom is clamped (`ZOOM_MIN`, `ZOOM_MAX`). The transform maths (`zoomAt`, `fitView`, `clampPan`, `revealBox`) are plain functions; test those, not pixels. A new diagram reuses the hook, and anything on the plane a press must reach (a card) carries `data-pan-ignore`.
- `Workspace` holds no layout of its own that a host or agent cannot set: where panels sit is a `WorkspaceLayout` (`columns[column][row]` of panel ids, shares of width and height, `hidden`), checked and repaired by `normalizeLayout` whatever its source, with at most four columns and four panels in a column. Panels are dragged with pointer events, not the browser's drag and drop, so a finger and a pen move them as a mouse does: a press on a heading becomes a drag after a few pixels, a chip with the panel's title follows the pointer, the drop zone under it is found with `elementFromPoint`, and Escape gives up. Every drag has a keyboard form (the "⋯" menu button in a panel's heading, which a right click on the heading also opens; arrow keys on a divider; the rail's buttons), a way that would change nothing is greyed out in the menu, and a move is announced. In a narrow container the columns stack and each panel is as tall as its content; a panel marked `fill` (content that scrolls inside itself, such as a conversation: the analytics chat's, the Playground's Agent and the Sample analysis thread) is given about a screenful below `--sf-sticky-top` instead. In the catalog an agent arranges it by sending `layout` ("search on the left, the map on the right" is `columns: [["search"], ["map"]]`), and a person's arrangement is reported back through `reportControls` as `layout`. The rail is icons only by default (about 40px wide), never vertical text, and each button's name shows at once on hover and on focus in the workspace's own tooltip (`.sf-workspace-tip`), not the browser's delayed `title`; Escape hides it, and the buttons carry their full names for assistive technology, so the tooltip is `aria-hidden`. With names turned on it is an icon over a short horizontal name (about 62px wide): a panel gives `shortTitle` when its title is longer than about ten characters (the rail clamps a name to two lines and the button's accessible name and tooltip are always the full title), `icon` is one of the built-in outline icons (`WORKSPACE_ICONS`) or the host's own node, and a panel with none shows its first letter; a button at the rail's foot switches between icons only and names, and `railLabels` with `onRailLabelsChange` lets a host hold that choice. A workspace inside another keeps its rail to icons and has no names to turn on. The last panel showing is `aria-disabled`, not `disabled`, so it can still be focused and say why it cannot be hidden. The layout is applied to an inner frame (`.sf-workspace-frame`), because a container's own box cannot answer its own size query; in a narrow container the frame stacks and the rail becomes a row above the panels. A panel shown from the rail goes back where it was (`places`): its own column again if it had one, its row in a shared column otherwise; a panel shown for the first time joins the last column while that holds fewer than two and takes a new column after that, and a new column takes a modest share so the others keep their proportions. A column keeps at most two panels open (`MAX_OPEN_ROWS`): opening or moving in a third folds the others to their headings (`collapsed`), a folded panel keeps its content mounted, and a column never has every panel folded. Test the layout functions, not pixels.
- `SideNav` unpinned keeps only the room its menu button takes: a slim strip where the navigation was, with the button at its top (`position: sticky` below `--sf-sticky-top`, never fixed to the window), so the button is never over the page or a host's toolbar and a host reserves nothing itself. Its names are built with `navigationName`, so a label that already ends in "navigation" is not said twice. Pressing it slides the navigation in from the left as a modal dialog: a drawer over a dimmed page where there is room, the whole of it where there is not. The drawer and the dimmed page are laid over the window, or, when the navigation is drawn inside a `.sf-container` region (a surface in a host's canvas, a chat reply), over the part of that region on screen and nothing outside it (`drawerBox`, measured when it opens and as the page scrolls or resizes, since a fixed box cannot be told its container in CSS; a region showing less than `SIDENAV_LEAST` px either way gives the drawer the window). The box is then counted from whatever the fixed stage is really placed against (`stageBox`): the window, or a holder or ancestor that is a containing block for fixed boxes (layout containment, a transform, a filter), found by measuring the stage itself, so the region's place in the window is never added twice. Test `drawerBox` and `stageBox`, not pixels. Focus goes to its close button and Tab stays inside; Escape, the close button, a press on the dimmed page or choosing a page closes it. Where the window, or that region, is under 40rem wide (`SIDENAV_NARROW`) it is always folded and has no pin, whatever `pinned` says; the choice comes back on a wider screen and puts focus back on the menu button. Hover and focus do not open it. Links from an agent go through `safeUrl`.
- `NodeGraph` is drawn with ECharts' graph series, the same ECharts `Chart` uses, and is never the only way in: every node is listed beside the canvas, and the list opens a node and walks to its neighbours, so it works with a keyboard and where no canvas can be drawn. Its layout settles and stops, and under reduced motion it is placed without moving. Past `limit` (300) it draws what is within two links of the open node, or of the most linked one, and says how many it left out; it never draws a hairball. Colour says what kind of thing a node is (`group`, a series colour each, named in the legend); how far along it is (`level`) is how full the node is drawn in that colour, since another hue would say "a different thing". Test `buildGraphOption` and `graphWindow`, not pixels. For tables and joins use `ModelDiagram`; for a pipeline, `PipelineGraph`.
- `DataSearch` takes `height`: with it the results scroll inside and the list can be focused; without it the list is as long as its results.
- **A menu is a shortcut, never the only way.** Use `useContextMenu` for right-click menus (a list of actions); settings or form controls gathered behind one button go in a `Popover`, never in a menu; every item must also be reachable by a key, a button or another control, and the menu itself must open from the keyboard (it does, through the `contextmenu` event). Keep the key table in [docs/accessibility.md](docs/accessibility.md) current when adding a shortcut.
- **Tables, columns and files are handed between components as `DataRef`s**: `{ sourceId, kind, catalog?, schema?, table, column?, path? }`, names only, never values or file contents. `ObjectBrowser` selects several (Ctrl or ⌘ click, Shift click, Space on the row the keyboard is on; Escape clears) and carries the whole selection when one of them is dragged or attached, or the one item otherwise. A drag writes the list (`DATA_REFS_MIME`), the first item in the older single form (`SCHEMA_REF_MIME`) and the names as plain text. Dragging between components uses the browser's drag and drop, which does not work by touch or keyboard, so the same hand-over is always on a row's menu and on Shift+Enter (`onAttach`). With one catalog and one schema the tree starts at tables, and a reference then names the table alone.
- **Where a store is has to reach the engine even with no credentials.** A DuckDB connection with an `endpoint`, `region`, `urlStyle` or `useSsl` and no secret is still registered with the engine (`secretSql`), so public data on a store that is not AWS is read anonymously from that store. Without this the engine asks AWS for the bucket. The repo's `surfaces.config.ts` adds the source `s3` when `SURFACES_S3_ENDPOINT` or `SURFACES_S3_BUCKET` is set (`SURFACES_S3_SECRET_NAME` names its credentials; none means anonymous), and `.claude/launch.json` has `data-s3` to start the dev server on the stand-in.
- **`FileBrowser` lists names, never contents.** It depends on `FilePlace` (`list(path, page)`) alone. A source's storage comes through `DataSource.listFiles` (optional; a backend without it leaves it out and the browser says so), which lists only the places the source may read: the DuckDB engine gives the folders of its registered tables and its connections' scopes, reads a local folder from disk after resolving where it really is (`..` and links cannot leave the roots), and lists an object store by prefix up to 5,000 entries, grouped by the next path part, with no sizes or dates (run against an S3 stand-in, not a real store). A folder from the person's computer is read by their browser (`showDirectoryPicker` where there is one, a folder input otherwise), hidden files are left out, and nothing is uploaded; its paths start at the folder opened, never above it. A file is handed on as a `DataRef` of kind `file` (`path`, with `sourceId` the source or `local:<folder>`), which `turnText` writes for a model, saying of a local file that it cannot be read. Opening a file is the host's decision (`onOpen`); the component loads nothing. Rows are windowed and folders load a page at a time.
- A browser's status line (`.sf-schema-note`) keeps one fixed line. Do not let it grow or collapse: the list above would change height and rows would move under a pointer between two clicks.
- Hidden columns in a grid are still fetched; hiding is a display choice. Column order, widths and hidden columns are plain data (`GridColumns`) so a host, a saved page or an agent can set them.
- SQL generated from a menu is offered (`onUseSql`) or copied; it is never run by the component.
- **A derived measure is arithmetic over aggregates, done by the engine.** `ViewQuery.derived` (`alias`, `expression`) names this query's aggregate aliases with numbers, + - * / and parentheses, and nothing else. One parser (`parseMeasureExpression` in `@surfaces-ui/data`) is used by the form that checks what a person typed, by `@surfaces-ui/sql` (which writes each name out as its aggregate, divides in floating point because Teradata would divide whole numbers as whole numbers, and guards a division by zero with `NULLIF`), and by `memoryDataSource`. The expression is parsed, never pasted into SQL. A chart measure takes `expression` with `terms`. Never work a rate out per row in SQL and average it, and never divide summarised cells in the browser.
- **What a person does is told to the agent as context.** Every component a person can change takes `onContext` and sends a `ContextNote` (`kind` such as `view.added`, `field.changed`, `filter.changed`, `point.selected`, `file.opened`; `summary`, the sentence the component showed the person; `subject`, the plain data it was about) for each thing they do. A note is not a request: it starts no turn and needs no `action`. In a surface a renderer passes `reportContext`, `SurfaceView` hands it to `onContext(componentId, note)`, and the host keeps the notes and sends them with the agent's next turn as `SurfaceState.activity`, once (`useChat`, `usePageStudio` and the Playground all do; `Chat` also takes `onContext` for a host that wants them as they happen). `turnText` writes them for a model as what the person did since its last reply, oldest first, marked as context and not requests. `reportControls` says where things ended up; a note says what happened on the way. A new interaction is not done until it sends one. Notes carry names and settings, and a value only where the person chose it (a filter's value, the bar they clicked); a file is named, never read.
- **One bar for choosing between a few views.** A switch between two to eight equal options (a mode, a view, light or dark) is a `SegmentedControl`, not a row of buttons drawn by hand: it gives the radio group, the keys and the sliding thumb. A `.sf-segment` may still be a `<button>` where the bar is a tab list or a set of toggles, and the base rule clears the browser's own border, fill and font for it.
- **The rows an app holds are a `DataTable`, never a table drawn by hand.** A list of people, invitations, jobs or keys that a host fetches from its own server is a `DataTable`, with `SelectionBar` for what to do with the rows chosen and `Pagination` beneath. The table sorts, filters and pages nothing (rule 2 holds for an app's rows too): a heading asks with `onSortChange`, and the host asks its server and hands over the page. "Select all that match" means the host acts on its search and filters, never on keys it does not have. Ask first for anything hard to undo with `useConfirm` (never the browser's `confirm()`), name the button for the action, and report what happened, with whom it left alone and why, in an `ActionReceipt` (`partial` when some were skipped). A status beside a row is a `StatusBadge`; a field that suggests as a person types is a `Combobox`. The rows of a query stay a `DataGrid`.
- **One set of item controls, everywhere.** Anything that lets a person change, move, resize or remove an item uses `ItemControls` with `standardControls(name, actions)`, which fixes the order, the wording and the icon of the shared actions: change, chart or table, wider, narrower, earlier and later (or up and down), duplicate, remove. Do not draw these as text buttons or with other glyphs (no "×" for remove). An action that makes no sense right now is passed as `false` and shown greyed but reachable; one an item never has is left out. Hover controls belong to a host with the class `sf-controls-host` (add `data-controls="corner"` to float them over its corner so nothing moves when they appear); they show on hover or focus inside, are always shown where there is no hover, and cannot catch a press while unseen. A control marked `pinned` stays in sight when the rest are quiet, for the one action a person must be able to find without pointing first (a report's "Add to report"); it is not pinned while it cannot be used, and at most one per item. **Only one layer of controls is on screen at a time**: an editor that frames components with its own controls puts `CONTROLS_QUIET` on the region while it is arranging, which hides the controls inside it, and passes `quietable={false}` on its own. Report tiles and the Playground's arrange bar both use this.
- **A metric is defined once, in a semantic model.** A `SemanticModel` (`semantic.proto`) is the agreed meaning of one set of rows: its rows (one read-only query on one source: a written query, or `tables` and `joins` it is generated from, the first table's rows being the model's rows), its `grain` (what one row is, in a sentence) and `primaryKey`, and its dimensions (a column to break rows down by), measures (one aggregate over one column, or a count) and metrics (arithmetic over measures only, worked out after summarising, never over another metric), names unique across all three, each field and join saying who defined it. A new model must say its grain and key, and the store refuses a key the engine finds repeated (`semanticKeyProblem`: one grouped query, no values back); a join that repeats rows fails that check, which is what keeps sums from double counting. Dimensions are plain columns; a computed one belongs in the query. Models do not link to each other yet. `Explorer` and `ReportBuilder` given `model` draw its fields as pills marked `model`; a person editing one makes a pill of their own, and "Add to the model" (key M) saves it into the model as a new version. A save names the version it was made against and is refused when that is stale (a new model is version 0, and a taken name is refused); the dev server also runs the query and checks the columns and key. **Making and changing a model leads with the agent**: it reads the tables with `describe_table` and proposes a whole model or a change by drawing `SemanticModelEditor` with `create` and `proposed` (`add`, `remove`, `rows`: grain, key, tables and joins, or `sql`); the person changes any of it (the joins in a `ModelDiagram` inside the editor, where a join the source declares is "Declared" and a guess stays "Inferred" and out of the query until confirmed) and only their save keeps it; their words go back as the `ask` event. Without an agent, `draftSemanticFields` / `draftSemanticModel` (`@surfaces-ui/data`) draft fields from column names and types only, labelled "generated from the columns", leaving out keys and personal data; the seeds' starter models use the same drafter. The patterns `create-a-semantic-model` and `change-a-semantic-model` hold the shapes. The dev server keeps one JSON file per model, with its versions, in `<storeDir>/semantic/` (`semantic: { dir, models }` in config); each seed starts with a model (`seedSemanticModels`). **A model's rows are drawn, not listed.** The editor opens on a `ModelDiagram` with `rowsFrom`: the first table marked as where the rows come from (and changeable), its detail laid out beside it, each join's kind on its line (`SemanticJoin.type`; an agent's join with none keeps every row of its left table, the nearer one, so adding detail never drops a row; a stored join with none is an inner join, which is what models saved before kinds ran), and a mark on any join that can repeat rows: from the keys the tables declare, or for a file with no keys from the engine on request (`mostRowsPerKey`, one grouped count). **The query a model's tables make must run on every engine.** Engines disagree about `SELECT *` over tables that share a column name (DuckDB renames, Teradata refuses it inside a query), so once the diagram has read the columns, `modelSql` names every column and gives a name a later table repeats its own alias (`order_id_1`, `outputColumns`), the same on every engine; with no repeated name it stays `SELECT *`. Join kinds are written `LEFT OUTER JOIN` and so on, which DuckDB, Teradata, DataFusion and Postgres all read. Run on DuckDB and on a real Teradata system; not yet on DataFusion or Postgres. A saved model keeps the query it was saved with until its tables or joins change. **A model can be built on a pipeline dataset.** `SemanticModel.dataset` (`pipeline_id`, `dataset`) says its rows are a dataset a pipeline builds: the query reads that dataset's table on the pipeline's source, and the grain and key are the dataset's, which the pipeline checks unique and not empty after every build. `semanticModelFromDataset(pipeline, name)` drafts one (fields from the dataset's declared columns and their descriptions, labelled as from the pipeline); `SemanticModelEditor` with a `Pipelines` backend offers "Start from a pipeline dataset" on a new model and source tables are not offered. `ModelLineage` shows the dataset's standing from its definition and latest run (`datasetStanding`; nothing is queried) in the editor, and as one line over an `Explorer` or `ReportBuilder` on the model, marked when the latest run failed, a check failed, the dataset was never built, or the model has drifted from it (`semanticDatasetProblems`: another source, a query that does not read it, another key, which the editor offers to put back). Rows written or joined by hand take the model off the dataset. An agent proposes one with `proposed.rows.dataset` (`pipeline`, `dataset`) plus the grain and key from `describe_pipeline`; `describe_semantic_model` reports `fromPipeline`. The dev server refuses a save whose dataset is gone or whose source or query is not the dataset's. Lineage stops at the dataset's own inputs (`Dataset.inputs`): it is not followed further upstream. Not built: links between models, column-level lineage, and running a model in a pipeline.
- **The builder starts from a phone.** `Explorer` answers to its own width through an inner frame (`.sf-explore-frame`): one column under 40rem, with the field list kept to a box of its own so the shelves stay near the pills, and fields beside the shelves above it. `ReportBuilder` tiles are one column, two from 36rem (a wider tile takes the row) and three from 60rem, where a tile's span holds. Shelves, headline numbers and item controls wrap rather than run past the edge.
- **A report is one document: pills once, filters once, views many.** `ReportState` holds the report's `fields`, its `filters` and its `tiles` (each a set of shelves, by pill id); the builder's shelves are its `draft`. A pill edited in the builder is the report's pill, so every tile that uses it changes; that is the point, and why a metric means the same thing in every tile. `normalizeReport` drops what cannot be drawn whatever sent it, but not before the pills exist (they are generated once the columns are known). A tile with no breakdown is headline numbers. At most 24 tiles. Use `ReportBuilder` for several views over one table or join; use separate `Chart` and `Metric` components on a page only when the views read different queries.
- A decimal comes back from the engine as its digits without the point. Anything that shows a summarised number reads it with `numericValue(value, type)`, never `Number(value)`.
- **`Explorer` holds nothing an agent cannot set.** Its pills and shelves are an `ExploreState`, plain JSON. With no `fields`, pills are generated from the query's columns by name and type only (`pillsFromFields`); `suggestDerived` offers calculations from the names and labels them as suggestions. Every pill says who made it (`by`: "the columns", "suggested from the columns", an agent, or the person's name), and a pill a person saves becomes theirs. A calculation is over metrics only, so one can never depend on itself; renaming a metric follows into the calculations that use it, and changing how a metric is summarised warns that they will change. Pills are dragged with pointer events (touch and pen work; a finger holds a pill for `TOUCH_HOLD_MS` before it drags, so a swipe over the pills still scrolls the page), onto a shelf or to a place along one (the order of the measures is the order of the series), and every drag has a key and a menu item: Enter puts a pill on its shelf, S splits by it, E edits, D duplicates, Alt+← and Alt+→ move it along its shelf, Delete takes it off, Shift+Delete removes a field the person made. How the chart is drawn is `ExploreState.chart` (`type`; `swap` for bars on their side, refused by `swapProblem` for anything but bars on one scale; `measures[id]` with `type` and `axis: "right"`), set by a person with the controls under the shelves or by an agent with the `chart` prop; a second scale still gets the chart's advice beneath it. The component never calls a model: `onAsk` hands the words to the host. In the catalog the agent sends `fields`, `rows`, `split`, `values`; a person's changes come back through `reportControls` in the same form, and the `ask` event carries their words.
- **Page-wide filters are one list in the page's data.** In the catalog a data component's `filters` is a list or a binding (`{ "@path": … }`); a `FilterBar` (drawn with `QueryFilters`) writes its list to that path, and every view bound to it follows. A `Chart` with `select: { path }` is a filter too: a click on a bar sets that column to the value (`toggleValueFilter`), a second click clears it, and the chart reads the list without its own column (`filtersExcept`) so the bars a person clicks stay; this is for a category x only. Views that share a list must read the same columns, since a filter on a column a view lacks fails. The bar reports its list through `reportControls` and its `change` event; `Chart` sends `select` with `column`, `value` and `series`.
- **A relative date is kept relative.** The `since` filter (`{ column, op: "since", values: ["30d"] }`; also `4w`, `3m`, `1y`, `week`, `month`, `quarter`, `year`) is turned into "on or after" when the query is sent (`filtersFromSpec`, `sinceStart`), from the start of a UTC day, so it moves once a day and never goes stale in a saved page. It lives in the plain form only: there is no `since` in the proto, and a filter read back from a query is `gte`. Never write "the last 30 days" as a date.
- **Every control a person can set, an agent can set.** Control state is plain JSON in the catalog: `sorts`, `filters` (`{ column, op, values }`) and `columns` on `DataGrid` and `QueryResult` (plus `view`), and `filters` on `Chart`, `PivotTable`, `Metric`, `Sparkline` and `BulletGraph`. An agent changes them by updating the component; a person can go on changing them by hand. Convert with `filtersFromSpec` and `sortsFromSpec`; filters that do not make sense are shown as a notice in place of the component, never ignored. A new control is not done until its state is a catalog prop, and until its renderer reports a person's changes through `reportControls` in that same prop form (`filtersToSpec`, `sortsToSpec`), so the agent sees them on its next turn (`SurfaceState.controls`).
- Lists that can be long (grid rows, `ObjectBrowser`, `SchemaExplorer`) render only the rows in view and fetch a page at a time. Keep it that way: no component may list a whole catalog or result in the DOM.
- `DataGrid` keeps a bounded cache of row blocks. Do not read "all rows" out of it; ask the backend (count, aggregate, export) instead.
- Components are tested against `memoryDataSource`. A new component needs a test that way, with no server.
- **The library traces itself when a recorder is above it, and only then.** `DataSourceProvider`, `DiscoveryProvider`, `PipelinesProvider`, `SemanticsProvider` (through `useDataSource` and their own hooks), `SurfaceView`, `useSurfaces` and `useChat` read `useRecorder()` from `@surfaces-ui/trace/react`. With none, nothing is recorded and nothing draws or behaves differently (`packages/spec/src/react/trace.test.tsx` compares the markup). With one: `useSurfaces` and `useChat` record each message (raw, upgraded, issues, applied or refused) under the key they hold the surface by (`s1:main`, `c1:m2:main`) and tag the surface object with it (`recorder.tag`), so `SurfaceView` records under the same key; a surface with no recorded messages (a saved page, a restored thread) is recorded whole as one `createSurface` (`surfaceSnapshot`). `SurfaceView` records each drawn component once (a child of the message that drew it), problems, data writes, control changes with a diff, actions with the contract result, and context notes; a component's service calls are children of the component (`TraceScopeProvider`, `useTraced`). One turn is one trace; a message recorded while a turn streams joins it. A new provider or hook that calls a backend or changes a surface is not done until it records through the same path, and anything it records must keep to the rule in `packages/trace`: names, SQL, counts, timings and errors, never row values or credentials. `SurfaceView` catches a component that throws while drawing (`ComponentBoundary`), shows the usual notice in its place and reports `RENDER_FAILED` through `onProblem`, with or without a recorder.
- **A component an app places itself is described once.** One that is not a catalog entry (it hosts the catalog, or is placed by the app rather than drawn by an agent) gets an entry in its package's `appComponents.ts` through `describeAppComponent`, and a demo in the playground's `appDemos.tsx`; `pnpm docs:gen` writes its page to `docs/components`, and the playground's Components area draws it under App components.
- jsdom has no layout: give `height` and `rowHeight` in tests, and test chart logic through `buildChartOption`.

Discovery rules:
- Components never call an embedding or language model. They call `Discovery`; the backend decides what may be indexed, embedded or sent to a model.
- **Data values are withheld by default.** Only names, types, descriptions and counts are indexed, embedded, profiled or put in agent context. A source must be listed in `allowSampleValues` before ranges, common values or sample rows appear anywhere. Never add a code path that embeds or sends row values for a source that is not listed.
- Generated text is a proposal. `describe` stores nothing; only `saveDescription` does, and it records whether a person or a model wrote the text. Never auto-save model output.
- Always show who produced an answer (`generated_by`). With no language model configured the backend answers with search results labelled `placeholder`; do not hide that label.
- SQL proposed by a model is shown and offered (`onUseSql`), never run automatically.
- Inferred joins are guesses from names and types and must stay labelled "Inferred". Foreign keys a source declares (`TableDetail.foreign_keys`) come back from `getRelated` with `inferred: false`, are labelled "Declared", and no guess is added beside them.
- A catalog surface navigates on its own: `DataSearch`, `ObjectBrowser`, `ObjectDetail` and `RelationshipGraph` take `opened: { "@path": … }` and write the opened table there; bind `ObjectDetail` and `RelationshipGraph` `table` to the same path. The event is still sent. Saved catalog pages and seed starters use `/table`.
- **Certification is a person's decision.** `setCertification` records who certified or deprecated an object, when and why. A model never sets it, and the controls appear only when the host passes `certifier` (who may certify is the host's rule; the dev server does not check). Certified objects rank higher in search and deprecated ones lower; neither is hidden. Show the mark with `CertificationBadge`, which uses text and a symbol as well as colour.
- Distinct counts in a profile are estimates (`distinct_count_estimated`); show them with "~".

**Pipelines** (optional; the one part of the library that changes data)

- `PipelineService` / `IngestService` and the `Pipelines` interface are separate from `DataSource`, which stays read-only.
- **A pipeline runs only definitions a person approved and the server checked.** Definitions come from `pipelines` in `surfaces.config.ts`, or, with `savedPipelines: true`, from `SavePipeline`: a whole `PipelineDraft` with `expected_version`, `approved_by` and `approval_digest` (`pipelineDigest`, sha256 of the draft's canonical protobuf JSON). The server refuses a stale version, a digest that does not match, a missing approver, a pipeline defined in config, and anything that fails the checks a run would make, then keeps it as `<storeDir>/pipelines/<id>.json` with every version. A save builds nothing. A run request names a pipeline, a selection and a refresh kind, never SQL; do not add a request field that runs SQL, a constraint or a path outside an approved save.
- Every dataset must itself be a single read-only query (`assertReadOnly`); the engine wraps it to build the table. A full refresh destroys data, so the server refuses it without `confirm_full_refresh` and the UI asks first.
- A dataset says what it reads (`depends`; left out, the names are worked out from the query and marked so), what one row is (`grain`), its `primaryKey`, `columns`, `tags` and `owner`. Row rules (`expectations`) warn, drop or fail per record before the build; **checks** run over the built dataset after it: `unique`, `not_null`, `relationships` (every value found in another table), `accepted_values` and `row_count`. A primary key adds a unique and a not-null check. Check SQL is written by `checkQuery` in `@surfaces-ui/sql` for every dialect, counts only, with values bound; `failingRowsSql` is offered, never run. A check that fails with severity `fail` (the default) marks the dataset failed (it stays built, as dbt leaves a model whose tests fail) and skips what reads it; `warn` reports it.
- `@surfaces-ui/pipelines` (`createPipelines({ pipelines, engineOf, runs, saved })`) is the reference runner on any `Engine` with `materialize`: dependency order, rules, build, checks, skips. `select` takes `name`, `name+` (and what reads it), `+name` (and what it reads). Runs carry `trigger` (manual, agent, cli) and `started_by`. Run history goes to a `RunStore` (the dev server keeps it in `<storeDir>/pipeline-runs/`, 50 per pipeline), so it survives a restart; a run cut short by a restart is shown cancelled. Built tables appear in the catalog and can be queried through `DataSource`. After a run the server drops kept results and rebuilds the search index.
- It recomputes whole datasets on every run. There is no incremental or streaming processing, no checkpoints and no schedule (run the CLI from cron). `Pipeline.recompute_only` says so, and the UI shows it.
- **Headless:** `surfaces-pipelines list | describe <id> | check <id> | run <id> [--select …] [--full-refresh --yes] [--json]` (in `@surfaces-ui/dev-server`) reads the same config and `.env.local`, and exits 1 when a build or a failing check fails, so CI and cron can use it.
- **Agents:** `pipelineTools(pipelines)` (`@surfaces-ui/agent`) gives `list_pipelines`, `describe_pipeline` (queries, grain, key, columns, checks and last state; never row values), `check_pipeline` (a dry run), `run_pipeline` (pauses for a person's approval; a full refresh is irreversible; what runs is the approved subject, refused if the pipeline's version moved), `get_run` and `propose_dataset`, which saves nothing: it returns the pipeline with the dataset, its digest and the version, for a `DatasetReview` (given `sourceId` and a new id, it proposes a new pipeline holding the dataset, at version 0, since a pipeline defined in config cannot be changed). The Playground's Pipelines page draws a `DatasetReview` over a pipeline kept in the page. `registerSurfacesApps` registers the same tools given `pipelines`; there `run_pipeline` is marked destructive for the host to confirm and offers no full refresh. `surfaceAgentPrompt(…, { pipelineTools: true })` tells the model how to use them. The dev server passes `pipelines` to a configured agent through `AgentServices`.
- `memoryPipelines(pipelines)` (`@surfaces-ui/data`) is a backend in memory for tests and demos: runs complete at once and query nothing; saves check the version, approver and digest.
- `inspectFiles` only reads a schema, and only from locations the source's engine is allowed to reach. `IngestWizard` produces configuration for a person to add; it does not register tables or load data.
- **dbt projects** (`@surfaces-ui/pipelines-dbt`): `dbtPipelines({ sourceId, read, invoke?, relationOf? })` is a `Pipelines` backend read from dbt's artifacts (`read: targetDir(dir)` from `@surfaces-ui/pipelines-dbt/node`): manifest.json gives the datasets (models, seeds, snapshots and sources), what each reads, the key (meta `primary_key`, a primary key constraint, or a column with both unique and not_null tests), owner, tags, `Dataset.relation` (where the built table is read: `schema.alias`, or `relationOf`) and every test as a check (unique, not_null, relationships and accepted_values in their own kinds; any other test and source freshness as `Check.description` text); catalog.json gives column types; run_results.json and sources.json give runs, test results as counts with dbt's own test query as `failingRowsSql` (offered, never run), and freshness. The grain is meta `grain`, or one row of the primary entity of a semantic model on it. dbt alone builds: nothing here runs a model's SQL or rebuilds a model from its compiled text, which `PipelineView` labels as a read-only preview (`Pipeline.externalRuns`). With `invoke` (`dbtCommand({ projectDir, profilesDir?, target?, command? })`, which spawns the dbt CLI with arguments as a list, never a shell, and keeps none of its output) a run a person starts, or an agent's `run_pipeline` a person approved, asks dbt to `build` (or `compile` for "Check only"), selecting by the project's own names checked against the manifest (sources refused), with `--full-refresh` only when confirmed; dbt's record of that invocation is taken in as that run. Without it the run buttons are replaced by "Built by another tool". Nothing can be saved (`canSave` false). `semanticModelsFromDbt(artifacts, { sourceId })` turns dbt's semantic layer (semantic_manifest.json) into starter models on the dbt datasets: dimensions and entities that are columns, measures with an aggregate here, and simple, ratio and derived metrics written out over one model's measures; a computed field, a percentile, a filtered, cumulative or conversion metric, and one spanning models are left out and listed in `skipped`, never approximated. A field without a description takes its dbt column's. `datasetStanding` counts a tool's own unique and not-null tests on the key as checking it, and counts warnings apart from failing checks. Dev server: `dbt: [{ sourceId, targetDir, relationPrefix?, build?: { projectDir, profilesDir?, target?, command? }, semanticModels? }]`; the projects are combined with the reference runner (`combinePipelines`, routing each call by pipeline id), a run started here drops kept results and rebuilds the search index when it ends, and a dbt semantic model whose name is taken is renamed after its project (`shop_orders`) with a warning. The repo's `surfaces.config.ts` adds one when `SURFACES_DBT_TARGET` is set, with `SURFACES_DBT_DATABASE` (a dbt-duckdb file, attached read-only as the source `dbt` under the name dbt gives it, so its compiled queries read the same tables), `SURFACES_DBT_PROJECT` and `SURFACES_DBT_COMMAND`. Run against a dbt-duckdb 1.12 project (a seed, staging views, a table with four tests, a semantic model with a ratio metric): its lineage, runs, checks, failing rows, a build started from the playground with a selection, and the semantic model in the Explorer. A DuckDB file takes one writer, so dbt cannot build into a file the dev server has attached: build it outside, or use a warehouse that takes several connections. Not run: dbt Cloud, a warehouse other than DuckDB, snapshots, incremental models, and the agent's `run_pipeline` on a dbt project with a live model.
- Not built: models reading datasets, schedules, incremental builds, building on Teradata or DataFusion with the reference runner, and dbt Cloud's API.

## Rules

1. **Contracts first.** A new cross-process call or stored document starts as a change in `proto/`, then `pnpm gen`. Do not hand-write types that mirror a proto message. Keep `buf lint` clean and do not make breaking changes to published messages.
2. **Sort, filter and page in SQL, never in the browser.** Grid and chart state is a `ViewQuery`; the engine side rewrites the base SQL in the source's dialect. Loading rows and filtering them in memory is a bug, not a shortcut.
3. **Every engine implements the same services.** DuckDB, Teradata and DataFusion are adapters behind `QueryService`/`CatalogService`. Nothing in `components` may know which engine it is talking to. Teradata is a first-class target: any SQL the library generates must have a Teradata form (no `LIMIT/OFFSET` there).
   **The data layer is removable.** UI packages (`tokens`, `components`, `chat`, `spec`, `app`) depend only on the `DataSource` interface and must never import an engine, driver, Connect client, `sql`, or the dev server. A consumer with their own backend implements `DataSource` and installs no data-layer package. Every component must run against an in-memory `DataSource`. See "Boundary" in [docs/plan.md](docs/plan.md).
4. **Colours and sizes come from `--sf-*` variables only.** No hex values, no fixed px for spacing or radius in component code or CSS. Need a new token? Add it in `packages/tokens/src/derive.ts` and `css.ts`, with a contrast test.
5. **One definition, generated everywhere.** Theme lives in `packages/tokens`; component catalogs (phase 4) will be defined once and generate types, validation, the agent prompt and docs. Do not copy constants between packages.
6. **MCP is one delivery channel.** Components must work as a plain React import. MCP Apps, A2UI-in-chat, embeds and standalone builds wrap the same components.
7. **Loom is an optional agent backend and is never vendored.** No Loom source, protos or binaries are committed here. `@surfaces-ui/agent-loom` (`loomAgent({ baseUrl, token })`) only calls a running Loom server's HTTP gateway and reads its JSON events. It reports Loom's agents and models (`describeAgents`, from `/v1/agents` and `/v1/models`, a model named `provider/model`) and, when a turn names a model the session is not on, switches the session first (`:switch-model`, keeping the conversation); tested on recorded calls, not yet against a live Loom.
8. **Do not copy code from loom-mobile.** It is the reference design only; implementations here are written fresh in TypeScript.
   The DuckDB engine refuses functions that hand a string of SQL to an attached database (`postgres_query`, `postgres_execute` and their MySQL and SQLite equivalents), because the read-only check cannot see inside the string. Keep that list current when attaching a new kind of database. Dates and times are handled in UTC whatever the server's own time zone.
9. **Read-only by default.** Query paths accept a single `SELECT`/`WITH` statement over a read-only connection. Credentials are referenced by secret name and resolved server-side; they never appear in protos, configs committed to a repo, or the browser. On the dev server, keys come from its environment or a git-ignored `.env.local` (`loadEnvFile`, which reports names, never values); there is no UI field for a key.
10. **Accessibility is part of done.** The standard is WCAG 2.2 level AA; [docs/accessibility.md](docs/accessibility.md) maps each criterion to how it is met and what is tested. Contrast is tested for presets; controls are keyboard reachable, labelled, with visible focus and at least `--sf-target-min` (24px, 44px for touch) to press; motion stops under `prefers-reduced-motion`.
11. **Respond to the container, not the window.** The same component is drawn in a page, a chat reply, a side panel and an MCP frame. Use `@container sf (...)` inside a `.sf-container` region (surfaces and query results already are), fluid grids before breakpoints, and no fixed widths.
12. **Charts follow Tufte and Few.** Bars start at zero, one y scale, sorted bars, no decoration, a text reading and a table for every chart. Run `chartAdvice` on a new chart shape. The full rules are in `plugins/surfaces-analytics/skills/chart-standards`.

## Conventions

- ESM, TypeScript strict, relative imports end in `.js`.
- Tests sit next to the code as `*.test.ts(x)` and run with Vitest; component tests start with `// @vitest-environment jsdom`.
- Packages export from `dist`; run `pnpm build` (or rely on Turbo's `^build`) before testing a package that depends on another.
- Sentence case in UI text. No decorative shadows.

## Querying data

```ts
import { collect, toRows } from "@surfaces-ui/data";
import { connectDataSource } from "@surfaces-ui/client-connect"; // or memoryDataSource, or your own DataSource

const data = connectDataSource({ baseUrl: "http://localhost:5220" });
const result = await collect(
  data.execute({
    sourceId: "lake",
    query: {
      baseSql: "SELECT * FROM orders",                       // the user's SQL, untouched
      sorts: [{ column: "amount", direction: SortDirection.DESC }],
      filters: [{ column: "region", operator: FilterOperator.EQ, values: [{ kind: { case: "stringValue", value: "Europe" } }] }],
      page: { limit: 50, offset: 0n },
    },
  }),
);
result.table;               // Arrow table holding only this page
result.header.executedSql;  // what the engine ran, for "show SQL"
result.header.notices;      // e.g. UNSTABLE_PAGE_ORDER
```

- Components take a `DataSource` prop or context; they never construct a client themselves.
- Change sort, filter or page by sending a new `ViewQuery`. Never sort or filter `result.table` in the browser unless it is the complete result.
- `ViewQuery` also carries `group_by`, `aggregates` (sum, avg, count, distinct, min, max, median, stddev, variance, percentile, approximate distinct), `buckets` (time grain or bin width) and `sample`. Each has a DuckDB and a Teradata form in `@surfaces-ui/sql`; add both, with golden tests, when extending it.
- **Kept results.** When an engine implements `store`, the server runs a non-trivial base query once into a temporary table and serves sorts, filters, pages, counts and charts from it (`ResultHeader.stored` says so and gives the time the data is as of). Plain `SELECT * FROM table` is never kept; results over `storedResults.maxRows` (250,000) fall back to live queries. Kept results are shared by everyone who can reach the server, so a multi-user server must add the user to the key.
- Filter values go in `Filter.values` and are always bound as parameters. Never build SQL by concatenating user input.
- Time travel: `timeTravel: { at: { case: "snapshotId", value }, table }` with an ID from `listSnapshots`.
- **Connections.** A DuckDB source can read tables from object stores and attach catalogs:

  ```ts
  { id: "lake", engine: "duckdb",
    connections: [{ name: "sales", kind: "s3", scope: "s3://acme-lake/sales", secret: "LAKE", region: "eu-west-1" }],
    tables: [{ name: "orders", format: "delta", path: "s3://acme-lake/sales/orders" }],
    catalogs: [{ name: "catalog", kind: "iceberg-rest", uri: "https://catalog.example.com/api", warehouse: "analytics", secret: "LAKE" }] }
  ```

  A catalog can also be a Postgres database (Supabase, Neon and RDS included), attached read-only: `catalogs: [{ name: "pg", kind: "postgres", uri: "host=db.example.com port=5432 dbname=shop user=reader sslmode=require", secret: "PG" }]`, with the password in `PG_PASSWORD`. Its tables are `pg.<schema>.<table>`. The address must not contain the password, and the login should be a role that can only read. Verified against Postgres 17 in a container (`scripts/seed-postgres.sql`, `packages/dev-server/src/postgres.test.ts`, which runs only when `SURFACES_TEST_POSTGRES` is set); not yet against a hosted database over TLS.

  `kind` is `s3` (also MinIO and R2 with `endpoint`), `gcs`, `azure` or `http`. `secret` is a name: `envSecrets` reads `LAKE_KEY_ID`, `LAKE_SECRET`, `LAKE_SESSION_TOKEN`, `LAKE_CONNECTION_STRING`, `LAKE_TOKEN` from the server's environment (pass your own `resolveSecret` for a vault). `ambientCredentials: true` uses the machine's cloud role. Only paths under a connection's `scope` can be read; a table that cannot be reached is reported by `testSource`, and does not stop the server starting. Never put a credential in config, a proto, a log or an error message, and never add a UI field for one.
- Keys and descriptions that files do not hold (Parquet has no keys) come from a table's `model` in config (`TableModel`: `primaryKey`, column descriptions, `foreignKeys`), applied by `withTableModel` and reported as `Column.primary_key`, `Column.comment` and `TableDetail.foreign_keys`. Declared foreign keys are facts; inferred joins stay labelled "Inferred".
- Adding an engine: implement `Engine` from `@surfaces-ui/engine`, add its dialect to `@surfaces-ui/sql` with golden tests, and pass it to `createSurfacesServer`.

## Agent-generated UI (A2UI)

Agents describe UI as A2UI v1.0 messages against a catalog; the client draws them with its own components. Read [docs/catalog/agent-prompt.md](docs/catalog/agent-prompt.md) for the message format and components.

```tsx
import { analyticsCatalog } from "@surfaces-ui/spec";
import { SurfaceView, analyticsRenderers, useSurfaces } from "@surfaces-ui/spec/react";

const { surfaces, apply, problems } = useSurfaces(analyticsCatalog);
// apply(message) for each message as it arrives from the agent
<SurfaceView surface={surfaces.main} catalog={analyticsCatalog} renderers={analyticsRenderers} onAction={sendToAgent} />
```

**Pages are documents.** A page, view or dashboard is a `PageDocument` (`@surfaces-ui/spec`): a title and a flat list of catalog components with a `root`. `pageSurface` draws it, `validatePage` checks it, and `editPage` applies `PageEdit`s (`set`, `update`, `remove`, `move` for layout, `title`, `theme`), refusing any the catalog does not allow. `PageStudio` (`@surfaces-ui/chat`) puts a page beside an instruction box: the words and the page go to an `AgentBackend`, its A2UI reply becomes edits (`editsFromMessages`), each instruction is one undo step, and the log shows who made each change. With `arrange` (off by default) a person can lay the page out by hand: each arrangement is one undo step, logged as "Arranged by" the `user`, and sent to the agent with the next instruction as a `layout.changed` note. `editsFromMessages` reads a whole message before deciding a child was dropped, so a component moved between containers is kept. A move keeps a Row's `sizes` and `widths` with the children they belong to, into another Row too (a newcomer fills, or takes the mean share); a Grid's `widths` are its columns' and stay. Where a drag lands is read from the page as drawn: a Row or Grid that has stacked drops above and below, beside takes the pointer resting at the outer tenth of a stacked element (`BESIDE_HOLD`, `BESIDE_EDGE`: a bar is held at its left end, so a drag straight up or down runs along that edge), a drop over the middle of a Card goes into the list it holds (`receiverOf`), resting at the left or right edge of the whole surface (`PAGE_EDGE`, the outer 24 px) puts the component in a column of its own beside everything (`besidePageMessages`: a stacked root keeps its id and padding and becomes a Row of that column, `PAGE_COLUMN_WIDTH` wide, and a Column of the rest; a root that is already a Row takes it as its first or last column), with a wider line down the page's edge and `toPageSide(id, side)` as its keyboard and menu form for a host to offer, and a drop where the component already is says so. The strip that takes a drop at a container's end lies over its foot (`data-overlay`) unless the container is empty, so starting a drag never moves the page. Examples are in `apps/playground/src/examples.ts`. Use `Grid` and `Metric` for dashboard layouts and headline numbers.

**Every component can appear in a chat thread.** The catalog holds the layout and summary components, the data components (`DataGrid`, `Chart`, `PivotTable`, `QueryResult`), the modelling and discovery components (`ObjectBrowser`, `ModelDiagram`, `DataSearch`, `ObjectDetail`, `RelationshipGraph`, `AskData`, `ContextBuilder`, `SqlEditor`) and conversation components (`Markdown`, `Message`, `Conversation` (a whole chat: thread, suggested replies, a box to write in, and scripted replies for a prototype), `CodeBlock`, `Table`, `Link`, `Checklist`, `Chips`, `DecisionCard`, `SqlProposal`), and `RowList` repeats one of them for each row of a query. A new component is not done until it has a catalog entry and a renderer. `ThemePicker` is the one exception (it changes the host page).

```tsx
import { Chat } from "@surfaces-ui/chat";

<DataSourceProvider dataSource={data}>
  <DiscoveryProvider discovery={discovery}>   {/* optional; discovery components say so when it is missing */}
    <Chat agent={agent} starters={["Show the data model"]} />
  </DiscoveryProvider>
</DataSourceProvider>
```

- `agent` is any `AgentBackend`. Chat never talks to a model or a transport itself.
- **A message can carry what it is about.** Tables and columns dropped on the `Composer`, or given through `Chat`'s `references` / `onReferencesChange` (so a browser beside the chat can add to them), show as chips with a remove button, go with the message as `SendRequest.references` (`ObjectRef`s), and stay on the sent message. `turnText` writes them out for a model, a table's database as part of its name. They are names; an attachment never carries or fetches values.
- Controls in a drawn component send an event back to the agent with what the person did: `DecisionCard` adds `choice`, `Chips` adds `value` (an item is its text or `{ label, value }`; with `selected: { "@path": … }` a press also writes the value into the surface's data, so a grid whose `sql` is bound to that path switches with no agent), `ModelDiagram` adds `sql`, `tables` and `joins`, `SqlProposal` and `SqlEditor` add `sql`. A renderer passes these as the second argument of `dispatch`.
- `SqlProposal` never runs on its own; a person presses Run, and it then goes through the read-only `DataSource`.
- An approval pauses the turn; the answer continues the same reply. **The backend checks every answer with `checkApproval` before acting** (digest of what the person saw, expiry, edits only when `editable`, a reason when required, `mayDecide` against the backend's own session, distinct people for `approvals_required`). `decided_by` comes from the client and is never trusted alone. Run the person's edited SQL or subject (`approved.sql`), never the model's original. Report what ran with `ActionReceipt`.
- Always show `generated_by` ("Answered by …"). A scripted or placeholder agent must say that it is one.
- **What a chat offers is the backend's to say.** Agents, models, skills and connectors come from `DescribeAgents`; a menu shows only what is listed and a turn carries only ids (`SendRequest.model`, `skill_ids`, `connector_ids`, with `choices_set` once a person chose). The backend refuses what it did not offer. A connector shows its status and a sign-in link the host opens (`onConnect`, through `safeUrl`); it never carries or asks for a credential.
- **A file a person attaches is the host's to read.** `attachFiles` gets the `File`s; what goes to the agent is a `DataRef` (a table the file became, or a file by name), never its contents. A file that cannot be used stays as a chip with the reason.
- **Voice is opt-in and says where audio goes.** Either pass `speech` only after the person chose it, or pass it with `speechConsent` (`given`, `onGive`): the microphone then shows, and its first press says where audio goes (`browserSpeech().label`: Chrome sends audio to Google) and listens only after "Use voice"; the host keeps the answer so it is asked once. A spoken conversation stops when a reply waits on an approval (that needs hands), on Escape, on its button, and after a long silence; the status is announced.
- **One setup menu, one model menu.** The agent, its skills and its connectors are set up once and rarely changed, so they share one composer button whose sections open in place (never as fly-outs, which break by touch and in narrow frames); the model is switched often, so it has its own. Where a model runs (its provider) is chosen with the model, in that menu, never in a separate picker.
- **Small lists are menus, big lists are panels.** A composer menu shows a few items and ends in "View all…" or "Manage…" (`onManage(panel)`), which opens its panel beside the conversation (`placeChatPanel`), never under it. Without a workspace, a menu lists everything.
- **What a host offers under a reply is the host's.** An `actions` part is never made from an agent's events; the host adds it to a thread it keeps, decides what each press does, and sets `outcome` when it is done. Alternatives that are one decision (three ways, one to apply, "Discard all") are one part with `choices`, so they share one group, one outcome and the buttons for the whole set.
- Surfaces are stored per reply, so two replies may both use the surface ID `main`.

**Human-in-the-loop patterns.** `patterns` (`@surfaces-ui/spec`, `packages/spec/src/patterns.ts`) holds a complete, valid surface for each moment a person must decide: connect a source, choose between sources, onboard to a dataset, review a cleaning plan, review personal data, review a transformation, confirm something irreversible. `patternMessages(pattern)` gives the A2UI messages; `docs/catalog/patterns.md` is generated from them; the docs app's Patterns page draws them live. An agent copies the shape. Add a pattern there, never as prose in a prompt, and keep its test passing (valid against the catalog, ends in a decision, anything that removes or replaces data is high risk).

Rules:
- **The wire format is A2UI v1.0, and v0.9 is still read.** Everything the library writes is v1.0: a binding is `{ "@path": "/a" }`, a function call `{ "@call": "name", "args": {} }`, the envelope keys on a component are `@catalogId`, `@accessibility` and `@metadata`, `createSurface` is sent once for a surface and may carry `components`, `dataModel` and `metadata`, and `updateDataModel` needs a `value` (`null` removes). Anything older is turned into v1.0 on the way in by `upgradeMessage` (inside `validateMessage` and `applyMessage`), `upgradePage` (inside every function that reads a `PageDocument`) and `upgradeSurface` (inside `SurfaceView` and `parseThread`); a page and a surface say which version they hold in `a2ui`, and one with none is read as v0.9. The rewrite walks the shape and is never a find-and-replace: a repeated child (`children: { componentId, path }`) and `updateDataModel`'s `path` keep their names. Not taken up from v1.0: functions called across the wire, catalogs mixed in one surface, `allowedParents`, `@checks` and `@index`.
- **Metadata is A2UI's `extensions`, and it is never drawn.** `@metadata: { extensions }` on a component, `metadata` on `createSurface` and on an action, and `metadata` on a json-render element and spec. A name is an identifier prefixed by its owner (`surfaces_locked`, `acme_ticket`); `a2ui_` is A2UI's. This library's own are `surfaces_theme` and `surfaces_expects` on a surface. A renderer never receives metadata as a prop, nothing in it is resolved or run, an unknown name is carried and ignored, and one component's is limited to `METADATA_LIMIT` characters of JSON. `updateComponents` replaces a component whole, so anything that rewrites a component must carry its `@metadata` forward (`editPage` and the Arrange messages do). Never put SQL that runs, or anything a component must show, in metadata: those are props.
- **An app adds its own components with `extendCatalog`.** `extendCatalog(analyticsCatalog, { id, title, description, components })` gives one catalog that draws everything the base does and the app's own, under the app's id; each added component takes `minHeight` like the base's (`withMinHeight`), and a name the base already has is refused. Its renderers are the base's with the app's spread in. Do not spread `analyticsCatalog.components` into `defineCatalog` by hand.
- **The basics are a catalog of their own.** `basicsCatalog` (`basics.ts`) holds the components every catalog shares: Text, Row, Column, Grid, Card, Divider, SideNav, Tabs, Button, the inputs and Form, Markdown, Link and ThemeSwitch, drawn by `basicsRenderers`. The analytics catalog lists the same definitions (`basicComponents`) in its own order, so its JSON, prompt and docs are what they were; a test checks that a basic component means the same under both. A catalog with no data components is built with `extendCatalog(basicsCatalog, …)`. Change a basic component in `basics.ts`, never in `analytics.ts`.
- **A site has a catalog of its own.** `siteCatalog` (`site.ts`) is the basics plus the components a page for people to read needs; it has no data components, and the analytics catalog has none of its. Hero takes its actions as `children` and Showcase names a child per entry of `examples`, so the outline, Arrange and removal find them like any child. A link an agent writes goes through `siteLink`: http, https or a path on the site (`/pricing`), never `//elsewhere` or a script. **A Media loads only what the page allows**: `MediaPolicyProvider` gives `resolve(name)` and allowed `origins`; with neither, the description is shown in its place, so an agent can never make a page load an address of its own choosing. Plan: [docs/plans/sites.md](docs/plans/sites.md); step 1 is built (this catalog), and a first slice of the Next.js adapter (`packages/next`: routes, metadata and sections, without layouts); the editorial preset, site patterns and skills, the site document with layouts, and running a site without Next.js are not.
- **A person's arrangement of a shipped page is a list of edits, not a copy** (`personal.ts`). `layoutEdits(page, messages)` turns what `useArrange` did into `PageEdit`s; `personalisePage(shipped, version, personal, catalog)` replays them over the shipped page, dropping (and reporting) only those that no longer fit, so a shipped page can improve without wiping what people arranged. A component with the `surfaces_locked` extension stays on the page: it can be moved and sized, `removeComponentMessages` refuses it, Arrange greys its remove control, and `layoutEdits` refuses a change that drops it. A stored layout is read with `parsePersonalLayout`. Where layouts are kept, and for whom, is the host's.
- **The catalog is the only source of truth.** Add or change a component in `packages/spec/src/analytics.ts` (description, Zod props, a valid `example`) and add its renderer in `react/renderers.tsx`. Then run `pnpm docs:gen`. Never hand-edit `docs/catalog`.
- **Nothing outside the catalog is drawn.** Every component is validated before rendering; unknown components, unknown props and malformed values show a notice instead. Do not add an escape hatch (raw HTML, arbitrary component names, style or script props).
- **Renderers treat values as text.** Never use `dangerouslySetInnerHTML` in a renderer. Links go through `safeUrl` (http and https only).
- **Only functions marked `action: true` can run from a control.** Other functions compute values. In an `action` a function call sits inside `functionCall`; a bare `{ "@call": … }` there is refused with a message that says so.
- **A refusal says how to correct it.** A value that fits no form of a union is reported as the problems of the form it came closest to (`flatten` in `catalog.ts`), and where no form is closer each union has its own message (`dynamic.ts`); a catalog message must never be the bare "Invalid input". The prompt writes every prop's shape (`shapeText`: `array of { column: string, desc?: boolean }`, `string | binding | call`), so a new prop needs no hand-written shape.
- **Any component can wait for a value.** `visibleWhen: { path, equals }` (or `in`; with neither, anything there) is part of every component's schema (`defineCatalog`), checked by `conditionHolds`, and `SurfaceView` draws nothing for a component whose condition does not hold. Loose inputs take `required` (and `pattern`, `min`, `max`) and say what is wrong beside the field once the person has left it, by the rules a `Form` uses (`checkSubmission`); a Button waits for loose inputs only when it names their ids in `requires`: while one of them is missing or wrong it is `aria-disabled` (never `disabled`, so it can be reached), and a press sends nothing, has each say what is wrong and moves focus to the first (`useInputCheck`, `useRequiredInputs`; an input that is not shown is not waited for). Values that must be stored, or checked by a backend, still belong in a `Form`, where a field waits on another field with its own `visibleWhen: { field, equals | in }` (`FormField.visible_when`): a field that is not asked for is not drawn, not required, and stored as null by every backend (`fieldAsked`, used by `Form` and `checkSubmission` alike).
- **A row of a query is drawn, never put in the data model.** `RowList` draws its `child` once per row through `RenderProps.rows`: the row is laid into a copy of the model at a place of its own (`/@rows/<id>/<n>`), so a relative path reads the row's column and an absolute one the surface, and a Button's event carries the row's key in the context its action declares. The surface's own data, and so what an agent is sent, never holds the rows; a relative write from inside a row is dropped. `formatString` takes `${path|words}` for a value that is not there yet.
- **Agent SQL is untrusted.** It reaches data only through `DataSource`, which is read-only. Do not let an agent's surface bypass it.
- Events from controls go back to the agent (`onAction`); the agent decides what happens next. The UI does not assume the outcome.
- **Containers lay out on the spacing scale.** `gap` (Row, Column, Grid) and `padding` (Row, Column, Card) take a step of the scale, `"none" | 1 | 2 | 3 | 4 | 6 | 8`, drawn as `--sf-space-<step>` through `data-gap` and `data-padding`; gap defaults to 4, padding to "none" (a Card's to 4). A Row takes `wrap` (default true; false keeps one line, even in a narrow container) and `sizes`, one per child: `"hug"`, `"fill"` or `{ fixed: px }` (24 to 1600), which wins over `widths` when both have one entry per child (`rowSizes`). A prop left out adds no attribute, so a page that uses none is drawn exactly as before. There is no pixel gap or padding: a new step is a new token first.
- **Every component can be given room.** A component whose catalog entry has no `height` takes `minHeight` (added to every such entry by `withMinHeight`), which `SurfaceView` applies to the component's box, whatever kind it is. `Row` and `Grid` take `widths`, one share per child or per column, used only when there is exactly one for each; narrow containers ignore them and stack. `Grid` takes `align` (`start`, `center`, `end`, `stretch`, the default) for where each child sits in its row's height; mixed content, such as a chart beside a form, takes `start`. A `Form` given more height than its fields keeps them together at the top. A person sets all three by dragging in an editor, and an agent by sending the prop.
- `SurfaceView` takes `frame(component, drawn)` for an editor: it wraps each drawn component in the editor's own element (a drag bar, an outline) and changes nothing else; the catalog checks, the data model and the events are the same with or without it. It is not a way to draw something the catalog does not hold.
- **The return path is a contract.** Each catalog event's context is typed with zod (`EventDefinition.context`) and published as JSON Schema (`x-events` in `catalogJson`). An agent may declare the `surfaces_expects` extension in `createSurface.metadata` (event name to JSON Schema); `SurfaceView` refuses to send an event that does not match and reports `CONTRACT_FAILED`. `useChat` sends `SendRequest.surfaces` (each surface's data model, controls and contracts) and `surface_errors` with every turn, and `data_model` with an action when the surface set `sendDataModel`. An adapter for a text-only runtime sends `turnText(request)`. Never add a path from a surface to an agent that skips `SurfaceView`'s checks. See [docs/agent-integration.md](docs/agent-integration.md).
- **One surface, three ways to write it.** A2UI components (what an agent sends), a json-render spec (`{ root, elements, state }`, with `{ $state }` bindings) and JSX markup (`analyticsMarkup` from `@surfaces-ui/spec/react`: `<Ui.Grid columns={2}><Ui.Metric … /></Ui.Grid>`, an element per catalog component taking exactly its props) all become the same components. `fromJsonRender` and `markupComponents` read the other two; `toJsonRender` and `toMarkup` write them; ids that are left out are made up from the kind (`metric`, `metric-2`), the root being `root`. `fromJsonRender` takes an explicit `typeMap` first, then a `Table` with `sql` as `DataGrid`, then any type that names a catalog component, then the older names (Box, Stack, Heading, Paragraph, StatCard). Only the outermost markup element draws (one `SurfaceView` over the compiled page); anything inside it that is not a catalog element is left out and noted. `analyticsMarkup` draws with `lazyAnalyticsRenderers`, so the renderers load when a page first draws; it is for catalog-checked surfaces, and app code that needs no checks imports the components from `@surfaces-ui/components`. `createMarkup(catalog, renderers)` does the same for another catalog; a catalog lists its component names in `names`, which is what types the elements. Each generated page in `docs/catalog/components` shows its example all three ways.

## MCP Apps

```ts
import { McpServer } from "@modelcontextprotocol/server";
import { registerSurfacesApps } from "@surfaces-ui/mcp";
import { readAppHtml } from "@surfaces-ui/mcp/node";

registerSurfacesApps(server, { dataSource, appHtml: readAppHtml });
```

- Tools for the model: `show_data_grid`, `show_chart`, `show_pivot_table`, `show_query_result`, `open_sql_editor`, `show_schema_explorer`, `render_surface`, `show_dashboard`, plus `list_tables` (with `search` and `database`; names only past 30 tables), `describe_table`, `search_data` (when a `discovery` backend is passed) and `get_component_docs` (no UI). Given `pipelines`: `show_pipeline` (draws `PipelineView`) and `propose_dataset` (draws `DatasetReview`), both filled in on the server so the model never copies a definition into a surface, plus the pipeline data tools. They return names, types and descriptions, never rows. Run live over stdio against Teradata (list, describe and a grid).
- A view is shown only after its SQL has run once on the server; a failure goes back to the model as a tool error it can correct. `render_surface` returns every catalog violation the same way.
- The app page fetches data through one tool, `surfaces_rpc`, which is hidden from the model, read-only and capped per request. Rows stay on the server except for the window on screen. Pipelines go through a second hidden tool, `surfaces_pipeline_rpc` (`mcpPipelines` on the page side), kept apart because it can change things, and only on a person's action in the page: a run they press (marked `manual`, "a person, in the MCP app", never a full refresh, which the page does not offer, `PipelineView` `fullRefresh={false}`) or a save they approved (the backend still checks approver, digest and version). The page's decision goes back to the conversation as the person's message; what they do along the way goes as model context (`updateModelContext`), not as a request.
- The MCP SDK is the split v2 packages (`@modelcontextprotocol/server`, `/client`, `/core`), which `@modelcontextprotocol/ext-apps` requires. Do not add the older `@modelcontextprotocol/sdk`.
- To install into another repo: `npx surfaces-mcp install --dir <repo>`, with a `surfaces.config.ts` there.
- The app page follows the host's theme: its light or dark mode, and the colours it shares in `hostContext.styles.variables` (the nearest preset, with the host's accent and corner radius, `themeFromHostStyles` in `@surfaces-ui/tokens`). The playground's hosts send the page's own theme with `hostStyleVariables`.
- Not verified in a desktop host (Claude Desktop and others): it has been run only through the docs app's in-page host and the stdio smoke test.

## Discovery and agent context

```tsx
import { DiscoveryProvider, DataSearch, ObjectDetail, ContextBuilder, addToContext, emptyContextDraft, tableRef } from "@surfaces-ui/components";
import { connectDiscovery } from "@surfaces-ui/client-connect"; // or createDiscovery({ dataSource }) from @surfaces-ui/discovery

<DiscoveryProvider discovery={connectDiscovery({ baseUrl: "http://localhost:5220" })}>
  <DataSearch onOpen={(object) => setOpen(object.ref)} />
  <ObjectDetail objectRef={tableRef("lake", "orders")} />
  <ContextBuilder value={draft} onChange={setDraft} />
</DiscoveryProvider>
```

- Server config (`surfaces.config.ts`): `discovery: { embedder: "local", allowSampleValues: ["lake"], storeDir: ".surfaces" }`. All three are optional; the defaults are keyword search, no data values, and `.surfaces`.
- Context packs are saved as JSON files in `<storeDir>/context/`, one per pack, so a consumer repo can review and commit them. `renderContextPack` returns the exact text an agent receives plus a token estimate.
- To plug in a model: pass `languageModel: { id, complete(prompt) }` or `embedder: { id, embed(texts) }` to `createDiscovery`, or implement `Discovery` yourself (for example on top of Loom).
- Not built yet: lineage (upstream/downstream), saved queries and documents as searchable objects, tags and owners, and exposing packs as an MCP resource (planned with the MCP phase).

## Using the theme

The styling guide for consumers is [docs/styling.md](docs/styling.md). The theme, the `--sf-*` variable names and `className` are public; `.sf-*` class names are internal and may change in any release, so never tell a consumer to style against them. `@surfaces-ui/components` ships `styles.css` and `styles.layer.css` (the same rules inside `@layer surfaces`, written by `packages/components/scripts/styles.mjs`); keep `@import`, `@charset` and `@namespace` out of `styles.css`, since a layer block cannot hold them.

```tsx
import { ThemeProvider, ThemePicker } from "@surfaces-ui/components";
import "@surfaces-ui/components/styles.css";

<ThemeProvider>            {/* sets --sf-* on :root, persists to localStorage */}
  <ThemePicker />          {/* presets, accent, radius, font, density, light/dark */}
</ThemeProvider>
```

- A host with a sticky bar of its own sets `--sf-sticky-top` to the bar's height, so library parts that stick as the page scrolls (`PageStudio`'s side) stay below it and end inside the window.
- Persist somewhere else by passing `storage` (any `StateStorage` from `@surfaces-ui/data`, the one interface the chat, the dev tools, a library and `persist` take too) and `storageKey`; pass `storage={null}` for memory only.
- Theme one region with `scope="scoped"`.
- Charts: `echarts.init(el, echartsTheme(theme, resolvedMode))` from `@surfaces-ui/tokens`.
- **Code colours are part of the theme too**: `--sf-code-keyword`, `-string`, `-number`, `-literal`, `-comment`, `-property`, `-function`, `-type`, `-punctuation`, derived from the chart hues or set in `theme.code.light/dark`, and always moved to 4.5:1 on the background and surfaces (tested for every preset). `CodeBlock`, `HighlightedCode` and `SqlEditor` use them; never colour code any other way.
- **Chart colours are part of the theme** (`theme.charts.light` and `.dark`): `series` (the categorical colours, in the order series take them), `sequential` (one hue for magnitude) and `diverging` (two poles around a neutral grey). They reach CSS as `--sf-series-N`, `--sf-sequential-1..7` and `--sf-diverging-1..7`, and reach ECharts through `echartsTheme`. Anything that draws data (a chart, a sparkline, a heat cell) uses these, never the accent or a status colour, and never a hex value.
- Series colours are a tested set, not a rotation of the accent. `HUES` holds thirteen hues built in OKLCH, with a light and a dark step (magenta, between pink and purple, leads Berry). The series hues do not share one lightness, on purpose: with red-green colour blindness red, orange, amber and green are one hue and teal, pink and magenta another, so within each family the steps differ in lightness (on light surfaces a crimson red and a forest green under a brighter amber and orange, pink and magenta below teal; on dark surfaces green and teal are the bright ones); yellow, mint and cyan are kept for tags and status, where a label goes with the colour. `SERIES_ORDERS` holds named orders (Classic, Aurora, Sand, Ink, Berry, Moss; Harbor and Mono use Classic), each the best order starting from its first hue by two measures: any two of the first five (`LEGEND_SLOTS`) are apart, neighbours or not, to full colour vision and under red-green colour blindness (`CVD_TARGET`), since a stack of five is read from its legend (blue, indigo and purple are never two of them), and neighbours anywhere stay apart under red-green colour blindness. Past five a chart still leans on its names and its table. An order's earlier forms are in `RETIRED_ORDERS` and the hues' earlier steps in `RETIRED_HUES`, and a saved theme holding either is moved to the current form when read (`currentSeries`, `currentHue`). `checkSeries(colors, surface)` reports neighbours that are too alike, two of the first five that are too alike (an error) or alike only under red-green colour blindness (a warning that says to make one lighter or darker), and colours that are faint against the surface; the picker shows it live and a test runs it for every preset on its own surfaces, and another checks that every series hue reaches 3:1 on every preset's panes. Add or change a hue or an order only with those tests passing in both modes.
- Series take colours in order and do not cycle. To keep a measure or a category the same colour everywhere, pin it: `y={[{ ..., slot: 2 }]}` or `splitSlots={{ Europe: 1 }}`. When a chart has more series than colours it says so.
- Eight presets: `Ink` (the library default: near-neutral greys with a trace of blue, indigo), `Aurora` (teal; the demo theme, and the docs app opens in Aurora, dark), `Sand` (natural greys with a warm yellow tint, a burnt orange with some brown), `Berry` (a deep pink-purple on plum greys that turn warm, toward wine, in the dark), `Harbor` (cool slate greys, a clear blue, with the Classic chart order), `Moss` (greys with a trace of green, warmer in dark, green) and `Mono` (black, white and greys with no hue in the chrome, a grey magnitude ramp, compact) and `High contrast` (black and white with no colour in the chrome, so only the data has colour, `contrast: "more"`; `ThemeProvider` then sets `data-contrast="more"` on the page so a host drops its own decoration, as the playground drops its glow). **`Theme.contrast: "more"`** draws a theme as the system's increased contrast would, whatever the person's own setting: edges at 3:1, tertiary labels at 7:1 and quaternary at 4.5:1, stronger dividers, solid glass, and every pane and control outlined through `--sf-color-edge` (transparent otherwise; `prefers-contrast: more` turns the same on). A pane or control that keeps a transparent edge writes `border: 1px solid var(--sf-color-edge, transparent)`.
- Presets keep the chrome quiet (near-neutral surfaces with a slight tint, one accent) so the colour on a page is the data, and each preset's charts open with its accent's hue. A theme saved before chart colours existed is given the default ones by `parseTheme`.
- **Colours come in ranges, each level made by the contrast it must reach**, not by a fixed share, so every theme keeps its tint and every level passes (`stepByContrast`, mixing in OKLab with `mixOklab`). `--sf-color-bg-1..4` (page, pane, raised item, deepest well), `--sf-color-label-1..4` (primary, secondary, tertiary at 4.5:1 on every background level, quaternary at 3:1 for disabled text and marks), `--sf-color-fill-1..4` (behind segments, chips and fields; primary text at 4.5:1 on each), `--sf-color-gray-1..6`, `--sf-color-divider` (quieter than `border`, between panes and rows where space already groups things) and `--sf-color-accent-hover` / `-pressed` (text on the accent stays at 4.5:1). Group with space and dividers before a box, and never put a box inside a box.
- **Glass is for controls that float over content, never for content.** `--sf-glass-regular` (toolbars, menus, the composer, tooltips), `--sf-glass-thick` (a sidebar, an inspector, a sheet) and `--sf-glass-clear` (a few icons over rich content, laid over `--sf-glass-dim`), with `--sf-glass-filter` for `backdrop-filter`, `--sf-glass-edge`, `--sf-glass-highlight` and `--sf-glass-shadow` (the one shadow the library has, and only on floating glass). Text on glass is `--sf-color-text` or `--sf-glass-muted`; clear glass carries icons and primary text only. Each is tested against the worst thing that can be behind it, a solid patch of any colour on screen, since blur only averages (`glassBackdrops`, `glassOver`, `GLASS`). `themeCss` turns glass solid for `prefers-reduced-transparency`, `prefers-contrast: more` and `forced-colors`, and nearly solid where `backdrop-filter` is missing.
- **Motion is timed by tokens**: `--sf-duration-fast` (a press, a hover), `--sf-duration` (a menu, a popover), `--sf-duration-slow` (a sheet, a drawer), with `--sf-ease`, `--sf-ease-out` and `--sf-ease-spring`, and `--sf-press-scale` for the shrink a press gives. Interaction is gummy: `--sf-ease-gummy` (a damped spring, `linear()` with a cubic fallback) over `--sf-duration-springy`. A press goes in at once and springs back on release (`--sf-press-time` and `--sf-press-ease`, quick under `:active`); the `.sf-segmented` thumb slides with the spring and squishes where it lands; a library control that switches on or off (`aria-pressed`, `aria-selected` tab, switch, checkbox) squishes once (`sf-squish-on`, `sf-squish-off`), only after a pointer or a finger changed it, never on load or under keyboard focus. `NavBar` slides one highlight per bar to the current section and page (`useIndicator`, measured offsets as `--sf-indicator-*`; placed without sliding when the list changes or resizes). Trees (`ObjectBrowser`, `SchemaExplorer`, `FileBrowser`) turn one caret (`data-open`) and glide the rows beneath on `top`; the library's `details` open to their height (`::details-content` with `interpolate-size`), a folded `Workspace` panel drops in when unfolded, and the chat's setup menu slides each section in from the side it is reached by. The playground's page change is an eased cross-fade of the page and its heading (`shell-page`): the new one comes into focus from a light blur and rises a few pixels, with no spring, since a spring starts fast and reads as a jerk on something that large. Under `prefers-reduced-motion` the durations are zero and a press does not shrink. Menus and popovers arrive with `sf-pop`, tooltips with `sf-fade`. The selected segment of any `.sf-segmented` is one thumb that slides between equal options, worked out from the markup with `:has()` (`data-thumb="off"` for one that wraps). `motion.test.ts` fails on any transition or animation not timed by the tokens. Nothing moves only to decorate.
- **Controls are fills, content is panes, nothing is a box in a box.** `.sf-button` is a fill (`--sf-color-fill-2`, a step stronger on hover, smaller when pressed), the primary action the accent; a field keeps a 3:1 edge. Cards, tiles and panels are a pane colour with a transparent edge (which forced colours draw); one inside another gives up its fill and edge. Floating parts (menus, popovers, tooltips, a drawer, the `NavBar`) are glass, and redefine `--sf-color-muted` as `--sf-glass-muted` inside. `.sf-glass` puts a host's own floating control on glass.
- **Type has a scale**: `--sf-font-size-xs`, `-sm`, the body size, `-lg`, `-title-3`, `-title-2`, `-title-1` and `-large-title`, with `--sf-font-weight-*`, `--sf-line-height` and `--sf-line-height-tight`. Size and weight carry hierarchy, so a heading needs no frame.
- **Density sizes the controls.** `--sf-control-size` (32px comfortable, 24px compact) is the height of every button, field, segment and icon button, used as `max(var(--sf-target-min), var(--sf-control-size))`, so a touch screen keeps its 44px targets in either density, where density still changes type, padding and spacing. A new control takes its size from these two tokens, never a fixed height. An icon in a button is drawn with `ControlIcon` (`close` takes a thing off; `remove` deletes it), never a text character such as ×, ✎ or ↑.
- **An agent can restyle, within limits.** `applyThemeRequest({ preset, mode, accent, radius, font, density, seriesOrder }, current)` applies what makes sense and reports the rest; it cannot produce an unreadable theme. Three places use it: the `surfaces_theme` extension in `createSurface.metadata` styles one agent surface only; a page's `theme` (the `theme` page edit) styles that page; and the `ThemeSwitch` catalog component changes the whole host page at once, says what changed and offers Undo.
- A theme from an untrusted place (agent output, URL, storage) goes through `parseTheme(input, defaultTheme)`.
- **A host's own themes are named like presets.** `ThemeProvider`'s `themes` (inherited by providers inside it) are chosen by name wherever a request names a preset: a page's `theme`, a surface's `surfaces_theme`, `ThemePicker` (after the built-in ones). Outside React they go to `applyThemeRequest(request, current, { themes })`, `editPage(page, edits, catalog, { themes })` and `presetByName(name, themes)`. A built-in name always resolves to the built-in preset, so a host cannot change what "Ink" means. `ThemeSwitch`'s catalog entry still lists the built-in names only.
