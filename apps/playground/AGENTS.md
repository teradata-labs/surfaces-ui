# `apps/playground`

Agent notes for this folder. The rules that hold everywhere are in the root [AGENTS.md](../../AGENTS.md). What you learn about this folder goes here.

| Path | What it is |
|---|---|
| `apps/playground` | One app, grouped Build / Components / Data / Library / Docs / Showcase, opening on a home page drawn from the site catalog (`homePage` in `areas/HomePage.tsx`: a Hero, a PromptReveal around a DeviceFrame, a Section of FeatureGrid role cards; the live dashboard and the data picker are the playground's own components added with `extendCatalog`), showing the playground building a dashboard on a desktop and an iPhone, paused by a button and shown finished under reduced motion and with a Showcase of setups by role (analyst, analytics engineer, data engineer, data steward, business leader, app and agent builder), each drawn live on a desktop and an iPhone (`areas/Devices.tsx`: the real components over the picked data, which a person can click, sort, filter and scroll; reaching into the home page's screens stops its demo on the finished page); changing area cross-fades the page and its heading under the bar with view transitions where the browser has them; with a sidebar data picker (the six seeds) and a backend badge. Components has a catalog area, opening on all components (`ComponentInventory.tsx`: a card each, drawn small from its catalog example over the picked data and only once near the screen, grouped as the list is, with one filter shared with the list, each card a link to its page): every catalog component with a preview that can be drawn in its own mode and theme (light or dark, any preset, without changing the page's), its code as React markup, A2UI and json-render (tabs, the choice kept), its props as a form drawn from the catalog's JSON Schema (`SchemaForm`: lists, numbers, checkboxes, value-or-binding, nested groups, JSON for the rest) or as highlighted JSON, both editing one value, live preview, declared events, the events sent, the data model, the props reference and the A2UI message; and an App components group (`AppComponentPage`, `appDemos.tsx`): each component an app places itself drawn live as a plain React component, its plain props in the same form, its parts that take code switched on and off (each filled with a working demo: the scripted agent, memory sessions, a pipeline), the JSX for what is on, and a log of its callbacks. Also: a SQL workbench (object browser, editor, result), a data model page (drag tables and columns to build joins, then query them), a pages gallery (example dashboards edited by plain-language instructions and arranged by hand in `PageStudio`, and a hand-built cross-filter dashboard), a chat page (a scripted demo agent drawing live components), three example pages in the gallery for every sample model (the area is now "Reports and pages"): "build a report" (`ReportBuilder`), "filter everything at once" (page-wide filters) and "explore with pills" (`Explorer`; on retail over `SALES_LINES`, one row per order line with its refund), the same Data panel on the Chat page switches between Tables and Files (`FilesPanel`: the picked source's storage and folders from this computer, also a panel in the Playground and a card on Sources; a Parquet, CSV or JSON file from this computer loads as a table when DuckDB runs in the page, and with the dev server it stays in the browser and the panel says so), a Sample analysis page (a seed's written conversation shown whole or played from the start, opening on one over the model picked in the sidebar, its components live, with the dashboard it ends in taken from the thread as a page to save and the conversation itself saved to the library as kind Conversation, which the Library draws as its thread), pipeline and sources pages, a Discover page (ask, search, table detail, connections, agent context), an MCP app page (the real app page in a sandboxed frame with this page as host), a patterns page (sparklines, bullet graphs, chart advice and every human-in-the-loop pattern drawn live with the event it sends back), a themes gallery and a theme editor. The Chat page puts an `ObjectBrowser` beside the conversation in a `Workspace`: drag a table or column onto the message box, or use "Add to chat". The Playground's instruction box takes the same drops. A Models page (Build) shows every agent backend within reach and the model each runs: the dev server's backends through `ModelService` (Claude, OpenAI, a local model and the test Loom; key status by variable name only, never a key field), the models on a local Ollama, and the provider and model the Playground, Chat, Pages and Semantic pages use (one choice, kept in the browser; each of those pages changes it from its composer's Model menu, grouped by provider: the scripted demo, the dev server's backend, Ollama on this machine, the test Loom; `providers.ts`). The test Loom runs a model on Ollama or Claude; changing it rewrites its looms.yaml and restarts that process, which inherits the dev server's environment so Claude's key reaches it as `ANTHROPIC_API_KEY` and is never written to the file (`SURFACES_TEST_LOOM_CONFIG`; a config on port 5018 is refused). The Playground area (first under Build, and where the app opens; in code and in its address it is still the composer, `/composer/`) draws the surface in one panel, with an Add control for any catalog component, and keeps its JSON and messages in another that can pop out into their own window kept in step over a `BroadcastChannel`; it has an agent beside the surface: the scripted demo, the dev server's agent (Claude, OpenAI or a local model, chosen by the server's environment so no key reaches the page), models on a local Ollama (called from the page with `dataTools` over the picked source), or agents on the test Loom (5028). An instruction sends the surface's components, data model and controls; the A2UI messages that come back are added to the message list and drawn; events from the surface go to the agent too (a checkbox turns that off). Its parts are panels of a `Workspace` sized to the window: Surface and Agent show to begin with, and a rail on the right shows and hides Components, Tables (real sources), JSON, Data model and controls, History (turns, events, saves, opens and hand edits, with restore to before any of them) and Save. A person drags, resizes and hides them, and the arrangement is kept in the browser; the agent conversation scrolls inside its panel and its instruction box stays in view. The app's own navigation is a `NavBar` across the top: Build, Components, Data, Library and Channels on glass, the current section's pages in a second bar, and the backend and an appearance menu (`ThemeMenu.tsx`: the eight presets, system, light or dark, and links to Themes and the Theme editor) at its end (in the menu on a phone). The data picker is not in the bar: it sits in the heading of each page that reads the picked data (beside the live screens on the home page), and the Library, Models and Sources have none, since each saved surface, model or source names its own data (`Area.data: false`); a saved surface's detail says what it reads. The open design work after the theme refresh is listed in [docs/plans/design-gaps.md](../../docs/plans/design-gaps.md). Components lists what the surface draws from the root down (`surfaceOutline`), and each one can be edited through a props form drawn from the catalog's JSON Schema, pointed at the table in hand ("Use table", real sources), or removed (`removeComponentMessages`, `setComponentMessages`, now in `@surfaces-ui/spec` and re-exported by `composerAdd.ts`); A2UI has no delete, so a removed component is dropped from its container and is not saved. "New surface" starts an empty surface and a new conversation, and History can bring the old one back. "Arrange" lets a person lay out what the surface draws (`useArrange`): each component gets a frame with a bar to drag it by, and is dropped above or below another, at either side of one in a stack to put the two side by side (they are wrapped in a two-column `Grid`; `besideMessages`), or at the end of a container. A handle under every component sets its height (its own `height` where its catalog entry has one, the `minHeight` of its box otherwise; `heightProp`, `heightMessages`), and a handle at its right edge in a `Grid` or `Row` sets that container's `widths` (`gridShares`, `slideShares`, `gridWidthsMessages`). A size is drawn as it changes (the surface is shown with the size applied) and sent as one `updateComponents` message on release, one step in History. Everything a drag does has a keyboard form: arrows on the bar, Up and Down in the Components panel, and arrow keys on the handles, with focus put back on the same control after the surface redraws. Dragging is done with pointer events, never the browser's drag and drop, so it works by touch and pen; a drag held near the top or bottom of the scrolling area scrolls it (`scrollFor`), since a finger on a bar cannot. Only containers with a `children` list give or take a component. **Sample data and real sources are kept apart.** The demo pages (Pages, the component catalog, Patterns, both theme pages, the MCP app, and the scripted Chat) are written against the six sample models and stay on sample data when a real source (one with no sample model, such as Teradata) is picked, with a note saying so. A source is real when it is neither one of the six sample models nor the sample orders (`isRealSource`): Teradata, a Postgres or DataFusion source, a bucket. A real source is worked on in the SQL workbench, Data model, Data catalog, Chat with a model, and the Composer. There the Composer starts empty; a "Tables in use" card (object browser, `useWorkingTables` in `tables.ts`, kept in the browser) holds any number of tables; the agent is told their columns and types (`tablesOutline`, never values) and the source's dialect; Add draws a data component from the table in hand only when the table has what the component needs (`tableProps`), and says what is missing otherwise; and the conversation opens with a guide written by the playground (`onboarding`: show what is here, build a starter dashboard, model how tables join), each choice a full instruction for an agent with `list_tables` and `describe_table`. Nothing is assumed about a real table's shape. **Dev tools.** The whole app is inside `SurfacesDevTools` (`main.tsx`; on while developing, absent from a published build and from `/view/`), so the drawer works on every page. The Playground area calls its agent itself, so it uses the explicit wrappers (`traceAgent`, `traceDataSource`) and records the agent's messages for reading (`replay: false`), its surface being recorded whole each time it changes; its own History panel is unchanged. **Docs** (`areas/DocsPage.tsx`, `/docs/<path under docs/>/`) draws the repository's guides with the library's `Markdown`: getting started, agent integration, accessibility, the recipes, the app components and the patterns, read from `docs/` when the site is built (loaded only when Docs opens), so the site and the repository never disagree; a link between guides opens in place, a link to a catalog component opens its Components page, a link into the code goes to the repository, and `docs/images` are served with the site. A link with `?theme=<preset>&mode=<light|dark|system>` opens the playground in that preset for the visit only (kept in memory, not the browser), and `/view/` (`areas/PageView.tsx`, `?page=n` for another example) draws one example page alone with no navigation, which is what the README's device and theme images and video 4 frame side by side. **Every page has an address of its own** (`routes.ts`): `/chat/`, `/docs/styling/`, `/catalog/Chart/`, with a page's own parameters in the query (`/library/?surface=<id>`) beside the site's (`source`, `theme`, `mode`). The app reads the path, moves between pages with `history` and never loads the page again (`go`, `onRoute`, and `followLinks` for any link to a page of the site); an address from before paths (`#chat`, `#docs?page=…`, `?component=Chart#catalog`) is moved to its path. The list of areas, their names and descriptions is `AREA_GROUPS` there, read by `App.tsx` and by the build. **The build writes a page of HTML for every route** (`prerender.tsx`, run by the `surfaces-prerender` plugin in `vite.config.ts` through Vite so it draws with the library's own `Markdown`): its title, description, canonical address and link preview (`public/og.jpg`), and its words in the body (each guide and catalog component's reference in full, the other areas their name, purpose and links), hidden from the first paint wherever JavaScript runs (a class set by an inline script in the head) so a person never sees them flash by before the app, and replaced by the app when it starts; plus `sitemap.xml`, `robots.txt` and a `404.html` marked not to be indexed. `SURFACES_SITE_URL` is where the site is served (the Pages workflow passes it). The guide list and its rules are `guides.ts`, read by the Docs page and the build. **Published to GitHub Pages** by `.github/workflows/pages.yml` on every push to main: built with `VITE_SURFACES_PUBLISHED=1` (`PUBLISHED` in `source.ts`), which never calls the visitor's own machine (no dev server, local model or Loom; the scripted demo is the only agent), and `SURFACES_BASE` taken from where Pages serves the site (`actions/configure-pages`: `/` on the custom domain, https://surfaces-ui.com, and the repository's path without one). Pages is turned on once in the repository's settings (Source: GitHub Actions). The published build, and no other, counts page views with Google Analytics (`analytics.ts`) when the repository variable `GA_MEASUREMENT_ID` is set: it sends which page of the playground was opened (`pagePath`, which leaves out a saved surface's id), never what a person typed or queried, and not at all for a visitor who sends Global Privacy Control or Do Not Track. Uses the dev server when it is running, DuckDB-wasm in the page when it is not (the lake sample and the six seeds, each loaded when first picked), and `memoryDataSource` if that fails. Resolves workspace packages to their source. |
