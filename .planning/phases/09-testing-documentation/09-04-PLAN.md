# Catalog API Reference

Complete reference for SurfacesUI json-render catalog components.

## Overview

The catalog defines 8 AI-specifiable components organized by atomic design:

- **Organisms** (1): SQLResultsDisplay - Complete SQL results with table/chart views
- **Molecules** (2): TableWithFilters, ChartWithControls - Composed multi-feature components
- **Primitives** (5): DataTable, Chart, Filter, DensityToggle, ViewModeToggle - Single-responsibility building blocks

## Component Specifications

### SQLResultsDisplay (Organism)

**Purpose**: Complete SQL query results display with table view, chart view, and export capabilities.

**When to use**: Displaying full SQL query results with visualization and interaction options.

**Props**:
```typescript
{
  initialViewMode: 'table' | 'chart' | 'both'; // Default view layout
  tableHeight: number;                         // Table container height in pixels
  chartHeight: number;                         // Chart container height in pixels
  chartType: 'bar' | 'line' | 'pie';          // Default chart visualization
  xAxis: string;                               // Column name for X-axis
  yAxis: string;                               // Column name for Y-axis
  allowExport: boolean;                        // Enable CSV export button
}
```

**Example spec**:
```json
{
  "type": "SQLResultsDisplay",
  "props": {
    "initialViewMode": "both",
    "tableHeight": 400,
    "chartHeight": 300,
    "chartType": "bar",
    "xAxis": "category",
    "yAxis": "value",
    "allowExport": true
  }
}
```

**Example prompts**:
- "Show SQL results with both table and chart"
- "Display query results as a bar chart with export button"
- "Create a complete view of the data with filtering and visualization"

**Context data provided**:
- `data`: Array of query result rows (Record<string, unknown>[])
- `savedConfig`: Persisted user preferences (table sort, chart axes)
- `onExport`: CSV export handler

## Catalog Constraints

### Prop Count Limits

Each component limited to 5-8 props for AI describability (json-render constraint):

| Component | Props | Status |
|-----------|-------|--------|
| DataTable | 4 | ✓ Within limit |
| Chart | 5 | ✓ Within limit |
| Filter | 2 | ✓ Within limit |
| DensityToggle | 1 | ✓ Within limit |
| ViewModeToggle | 1 | ✓ Within limit |
| TableWithFilters | 6 | ✓ Within limit |
| ChartWithControls | 7 | ✓ Within limit |
| SQLResultsDisplay | 7 | ✓ Within limit |

### Context Data vs Props

Components receive data from two sources:

1. **AI-specifiable props**: Configuration values the AI can set (defined in catalog schema)
2. **Context data**: Runtime data provided by application (rows, callbacks, state)

**Why this matters**: AI generates props only. Context data comes from your application via SurfacesRenderer.

**Example**:
```tsx
// AI generates this spec:
const spec = {
  type: 'DataTable',
  props: { columns: ['id', 'name'], sortable: true }, // AI-specifiable
};

// Your app provides context data:
<SurfacesRenderer
  spec={spec}
  context={{
    data: queryResults, // Context data (not AI-specifiable)
  }}
/>
```

- `--background`, `--foreground` - Base colors

- `--border`, `--input` - UI element colors
- `--spacing-*` - Spacing scale
- `--font-*` - Typography scale

Density variants scale spacing via CSS custom properties (0.8x compact, 1.0x comfortable, 1.2x spacious).

# Integration Guide

How to integrate json-render components into existing SurfacesUI applications.

## Overview

This guide covers:
1. Installing json-render packages
2. Using SurfacesRenderer in your app
3. Migrating from direct component usage to catalog specs
4. Integrating with MCP Bridge for tool calls
5. Natural language UI generation

## Installation

```bash
pnpm add @json-render/react @json-render/core
```

Already included in `@surfacesui/components@0.1.0`.

## Quick Start

### 1. Render a Static Spec

```tsx
import { SurfacesRenderer } from '@surfacesui/components';

const spec = {
  type: 'DataTable',
  props: {
    columns: ['id', 'name', 'email'],
    sortable: true,
    height: 400,
  },
};

const data = [
  { id: 1, name: 'Alice', email: 'alice@example.com' },
  { id: 2, name: 'Bob', email: 'bob@example.com' },
];

function App() {
  return (
    <SurfacesRenderer
      spec={spec}
      context={{ data }}
    />
  );
}
```

### 2. Generate Spec from Natural Language

```tsx
import { NLGenerator, SurfacesRenderer } from '@surfacesui/components';
import { useState } from 'react';

function App() {
  const [spec, setSpec] = useState(null);
  const [data, setData] = useState([]);

  return (
    <div>
      <NLGenerator
        baseUrl="http://localhost:8000"
        renderSpec={(generatedSpec) => setSpec(generatedSpec)}
      />

      {spec && (
        <SurfacesRenderer
          spec={spec}
          context={{ data }}
        />
      )}
    </div>
  );
}
```

### 3. Integrate with MCP Bridge

```tsx
import {
  SurfacesRenderer,
  McpBridgeProvider,
  McpAppsBridge,
} from '@surfacesui/components';

const bridge = new McpAppsBridge();

function App() {
  return (
    <McpBridgeProvider bridge={bridge}>
      <SurfacesRenderer
        spec={spec}
        context={{ data }}
        bridge={bridge} // Enable MCP actions
      />
    </McpBridgeProvider>
  );
}
```

Components can trigger MCP tool calls via actions (e.g., execute_sql, export_csv):

function ResultsView({ spec, data }) {
  const bridge = useMcpBridge();

  // Create action handlers for MCP tools
  const handlers = createMcpActionHandlers(bridge);

  return (
    <SurfacesRenderer
      spec={spec}
      context={{ data }}
      bridge={bridge}
      onAction={handlers}
    />
  );
}
```

# Registry Extension Guide

How to add custom components to the json-render catalog and registry.

## Overview

The registry maps catalog specs to React component implementations. Extending it allows:

1. Adding custom components not in base catalog
2. Overriding default component implementations
3. Injecting custom context data patterns
4. Supporting organization-specific UI patterns

## Architecture

### Catalog → Registry → Renderer Flow

```
AI generates spec → Catalog validates → Registry maps → Renderer displays
     JSON             Zod schema          React       Component tree
```

**Catalog** (`schema.ts`):
- Zod schemas defining AI-specifiable props
- JSON structure LLM can generate

**Registry** (`registry.tsx`):
- Maps component types to React implementations
- Wraps components to inject context data
- Uses ComponentContext pattern for json-render integration

**Renderer** (`renderer.tsx`):
- Takes validated spec + context data
- Passes to json-render with registry
- Applies theme/density providers

## Adding a New Component

### Step 1: Define Catalog Schema

Create Zod schema with 5-8 props max:

```typescript
// src/catalog/schema.ts
import { z } from 'zod';

export const MetricCardSchema = z.object({
  type: z.literal('MetricCard'),
  props: z.object({
    title: z.string().describe('Card title'),
    value: z.number().describe('Metric value'),
    trend: z.enum(['up', 'down', 'neutral']).optional(),
    unit: z.string().optional().describe('Value unit (%, $, etc)'),
    comparison: z.string().optional().describe('Comparison text'),
  }),
});

export type MetricCardSpec = z.infer<typeof MetricCardSchema>;
```

**Key constraints**:
- Max 8 props (AI describability limit)
- Descriptions under 60 chars
- Use .optional() for non-required props
- Use z.enum() for limited choices

```typescript
// src/catalog/types.ts

### Step 4: Create Registry Wrapper

Wrap component to inject context data using ComponentContext pattern:

```typescript
// src/catalog/registry.tsx
import { ComponentContext } from '@json-render/react';
import { MetricCard } from '../primitives/metric-card';

// Add to registry object:
export const registry = {
  // ... existing components
  MetricCard: (props) => (
    <ComponentContext.Consumer>
      {(ctx) => {
        // Extract context data
        const contextData = (ctx as any).data?.value;

        return (
          <MetricCard
            title={props.title}
            value={props.value}
            trend={props.trend}
            unit={props.unit}
            comparison={props.comparison}
          />
        );
      }}
    </ComponentContext.Consumer>
  ),
};
```

**Why wrappers**: json-render requires functional components with context access. Direct component imports don't have access to context data.

## Advanced Patterns

### Handling Context Data

Components receive data from registry wrappers:

```typescript
MetricCard: (props) => (
  <ComponentContext.Consumer>
    {(ctx) => {
      // Access shared context
      const data = (ctx as any).data?.value;
      const theme = (ctx as any).theme;

      // Compute derived values
      const actualValue = data?.metrics?.[props.title];

      return (
        <MetricCard
          {...props}
          value={actualValue ?? props.value}
        />
      );
    }}
  </ComponentContext.Consumer>
),
```

**Use cases**:
- Fetch data from shared context
- Access theme/density settings
- Wire callbacks to parent handlers
- Transform data for component consumption

### Type Safety

Use explicit interfaces for type checking:

```typescript
interface RegistryProps {
  title: string;
  value: number;
  trend?: 'up' | 'down' | 'neutral';
}

const MetricCardWrapper = (props: RegistryProps) => (
  <ComponentContext.Consumer>
    {(ctx) => <MetricCard {...props} />}
  </ComponentContext.Consumer>
);

export const registry = {
  MetricCard: MetricCardWrapper,
};
```

Avoids `as any` casts and provides IDE autocomplete.

### Memoization for Performance

Use useMemo for expensive context transformations:

```typescript
MetricCard: (props) => (
  <ComponentContext.Consumer>
    {(ctx) => {
      const data = (ctx as any).data?.value;

      // Memoize expensive computation
      const processedData = React.useMemo(
        () => processMetricData(data),
        [data]
      );

      return <MetricCard {...props} data={processedData} />;
    }}
  </ComponentContext.Consumer>
),
```

Important for large datasets or virtual scrolling.

      props: { title: 'Sales', value: 100 },
    };
    expect(MetricCardSchema.safeParse(valid).success).toBe(true);
  });

  it('rejects invalid value type', () => {
    const invalid = {
      type: 'MetricCard',
      props: { title: 'Sales', value: '100' }, // Should be number
    };
    expect(MetricCardSchema.safeParse(invalid).success).toBe(false);
  });

  it('enforces prop count limit', () => {
    const tooManyProps = {
      type: 'MetricCard',
      props: {
        title: 'Sales',
        value: 100,
        prop3: 'a',
        prop4: 'b',
        prop5: 'c',
        prop6: 'd',
        prop7: 'e',
        prop8: 'f',
        prop9: 'g', // 9 props exceeds 8-prop limit
      },
    };
    expect(MetricCardSchema.safeParse(tooManyProps).success).toBe(false);
  });
});

## Best Practices

1. **Atomic Design**: Keep components small (<400 lines, single responsibility)
2. **Prop Limits**: Stay within 5-8 props for AI describability
3. **Context Usage**: Use ComponentContext for runtime data, not AI-specifiable props
4. **Type Safety**: Define explicit interfaces, avoid `as any` where possible
5. **Performance**: Memoize expensive operations, especially for virtual scrolling
6. **Testing**: Cover schema validation, rendering, and context injection
7. **Documentation**: Add component to catalog prompt with examples

## Troubleshooting

### "Component not found in registry"

Verify:
1. Component added to registry object with correct name
2. Name matches `type` field in spec exactly (case-sensitive)
3. Registry exported from `src/catalog/index.ts`

### Context data not accessible

Verify:
1. ComponentContext.Consumer wrapper present
2. Context data passed to SurfacesRenderer: `context={{ data: ... }}`
3. Accessing `(ctx as any).data?.value` pattern used

### Props not type-safe

Use explicit interfaces:
```typescript
interface WrapperProps {
  title: string;
  value: number;
}

const Wrapper = (props: WrapperProps) => (
  <ComponentContext.Consumer>
    {(ctx) => <Component {...props} />}
  </ComponentContext.Consumer>
);
```
