# `plugins`

Agent notes for this folder. The rules that hold everywhere are in the root [AGENTS.md](../AGENTS.md). What you learn about this folder goes here. A plugin's own folder holds no `AGENTS.md` or `CLAUDE.md`: everything in it is shipped to whoever installs it, and Claude Code does not load an instructions file at a plugin's root.

| Path | What it is |
|---|---|
| `plugins/surfaces-analytics` | A Claude Code plugin of skills for data and analytics agents: `chart-standards` (Tufte and Few), `dashboard-design`, `human-in-the-loop`, `connect-and-onboard`, `data-cleaning`, `personal-data`, `data-transformations`, `responsive-accessible-ui`. Listed in `.claude-plugin/marketplace.json`, so `/plugin marketplace add <this repo>` then `/plugin install surfaces-analytics@surfaces-ui` installs it. It also starts the Surfaces MCP server (`.mcp.json`). Skills state rules and point at the catalog and patterns; they must not restate component props (those come from `docs/catalog`). Installed from this repository's marketplace into Claude Code 2.1.332 and run in a headless session: the eight skills were listed, the MCP server started from the pinned package with the sample data, and `list_tables` answered. The skills themselves have not been exercised on real tasks. |
| `plugins/agent-notes` | A plugin for any repository, not only this one: the skill `notes-upkeep` (where a fact goes, writing, splitting and pruning notes, moving a repository from one long file to notes beside the code), a hook (`skills/notes-upkeep/scripts/notes-guard.mjs`) that refuses a write to a folder whose notes are not in context, and `check-notes.mjs` for CI. **This repository runs the same two scripts from here** (`.claude/settings.json`, `pnpm check:notes`, settings in `.agent-notes.json`), so there is one copy; a change to either changes how this repository's own notes are guarded. ## Rules

- **`surfaces-analytics` is for everyone who works with data through an agent**, not only for people building an app: its skills are about judgment (charts, dashboards, cleaning, personal data, approvals), and its MCP server works with no code written. Do not make a skill depend on the reader having a Surfaces UI app.
- **It starts the MCP server, pinned.** `.mcp.json` runs `npx -y @surfaces-ui/mcp@<version>`, the exact version this repository publishes; `pnpm version-packages` sets the pin and raises the plugin's version (`scripts/check-plugins.mjs --write`), and `pnpm check:plugins` fails when the pin is behind. With no config and no settings the server serves the sample data, so the plugin works straight after install. It looks for a config in its working directory (the project folder in a Claude Code session, seen live; not promised by the docs) and then in `.surfaces` in the person's home directory.
- **A plugin's version is its own, and nothing reaches people who installed it until it changes.** Claude Code and the directory both compare versions: a change to a skill, a hook or the README with the same `version` in `plugin.json` is not picked up (`claude plugin update` answers "already at the latest version"; seen with a description change left at 0.4.0). Raise `version` in the same change as anything under a plugin's folder.
- **Skills stay portable.** A `SKILL.md` has `name` (its folder's name) and `description` in its front matter and nothing else, so it loads in any agent that reads Agent Skills. Anything a skill runs sits inside the skill's own folder (`scripts/`), so the folder can be copied alone.
- **Each plugin is submitted to Claude's directory on its own**, as this repository plus its folder as the plugin path (https://claude.com/docs/plugins/submit). `pnpm check:plugins` mirrors what a submission is refused for: the manifest's name, description, author, version and license; a README of 40 words that says what the plugin runs, reads and sends; nothing but text and images, each under 256 KiB; a hook command that names its script from `"${CLAUDE_PLUGIN_ROOT}/"` with no other variable; a launcher pinned to an exact version; no credentials. Two things are held for a reviewer by design and are said in each README: `surfaces-analytics` starts a pinned `npx` package, and `agent-notes` runs a Node script from a hook, which the directory's validator cannot follow.
- A plugin is also installed straight from this repository's marketplace (`.claude-plugin/marketplace.json`): `/plugin marketplace add teradata-labs/surfaces-ui`, then `/plugin install <name>@surfaces-ui`. A new plugin gets an entry there, and `pnpm check:plugins` fails without one.
- **What each Claude app loads from a plugin is not the same**, by Anthropic's own table (https://claude.com/docs/plugins/platform-support, read November 2026). Skills load everywhere. A plugin's local stdio MCP server loads in Claude Code and the desktop app's Code tab, and in Cowork only when the session runs on the person's computer; **a chat ignores it**, on the desktop too. Hooks and agents load in Cowork and Code, not in chat. A top-level `bin/` makes chat and Cowork refuse the whole plugin, so never add one. A server whose `${user_config.*}` reference has no `default` is ignored in Cowork, which never asks for values, so **every setting has a default** (`sample data`, or empty), and the server reads an unfilled one as not set (`configFromEnv`).
- **So `surfaces-analytics` reaches a desktop chat only as skills.** Its interactive views there need the server added by hand (Settings, Developer, Edit Config; the README has the entry) or a remote `https://` server listed as a connector, which is not built. The directory no longer lists desktop extensions (`.mcpb`); it says to put a local server in a plugin bundle. Whether an MCP App from a plugin's server is drawn in Cowork or the Code tab is not stated in the docs and has not been seen.
- **Settings** (`userConfig` in `plugin.json`): database type, the database's MCP server, the connection string (`sensitive`, so it goes to the credential store) and the name it is passed under. `.mcp.json` hands them to the server as `SURFACES_SOURCE_*`. Run in a headless Claude Code session from a local copy of the plugin pointed at this checkout's build: installed with `--config`, the server listed a Postgres database's tables through that database's MCP server. The published package the real plugin pins does not read these until the next release.
- **The icon** (`.claude-plugin/icon.png`, 1024 px, drawn from the playground's `favicon.svg`) is what the directory shows, and it is taken only the first time the plugin is saved or submitted there; a later change to the file does not change the listing.
- Not done: neither plugin has been submitted to the directory; no `claude plugin eval` suite; nothing has been tried in Cowork or a desktop chat; `agent-notes` has no icon.
